# Архитектура API — слои, правила, тесты

Как устроен `backend/api/`: за что отвечает каждый слой, что ему запрещено, чем
проверяется и что считать готовым.

Документ для того, кто садится дописывать разделы. Контракт — [api.md](api.md),
схема данных — [database-architecture.md](database-architecture.md).

Состояние на 8 августа 2026: реализованы служебные эндпоинты и вход целиком —
8 операций из 46. Каркас стоит, разделы дописываются по одному.

---

## 1. Раскладка

```
backend/
├── database/
│   └── models.py            16 таблиц, источник правды для миграций
└── api/
    ├── main.py              сборка приложения, префикс, OpenAPI
    ├── settings.py          окружение
    ├── db.py                движок и сессия
    ├── deps.py              кто пришёл, что можно
    ├── security.py          пароли, JWT, refresh
    ├── errors.py            problem+json
    ├── schemas/             Pydantic по разделам
    │   ├── common.py        User, WarehouseBrief, Page, Permission
    │   ├── auth.py
    │   └── service.py
    ├── routers/             один файл на раздел api.md
    │   ├── auth.py          ✔ 4 операции
    │   └── service.py       ✔ 4 операции
    └── services/            правила и границы транзакций
        └── visibility.py    ✔ фильтр по своему складу
```

**Разделено по слоям, а не по домену.** Исходный план в
[database-architecture.md §3.3](database-architecture.md) предлагал шесть
доменных сервисов, каждый со своими моделями. От него отказались: посмотрите на
«отгрузить» — одна транзакция пишет в `order`, `shipment`, `stock_balance` и
`stock_movement`. Три «сервиса» из шести. То же в «принять заказ» и «завершить
приёмку». Границы протыкались бы ровно в тех трёх местах, ради которых система
существует, — это не границы, а декорация с узаконенными исключениями.

## 2. Правило зависимостей

```
routers  ──▶  services  ──▶  models
   │             │
   └──▶ schemas  └──▶ deps · security · errors · db · settings
```

Смотрят только вниз. Роутер зовёт сервис, сервис — модели; обратно никто не
смотрит.

Правило проверяемое, а не на честном слове: `check_layers.py` разбирает импорты
через `ast` и ищет запрещённые вызовы. Осознанные исключения лежат в нём же, в
`KNOWN_LEAKS`, каждое с причиной — и если исключение перестало быть нужным,
проверка потребует убрать его из списка. Сейчас там одна запись:
`routers/auth.py` управляет транзакцией, разбор в 3.3.

```
$ python3 check_layers.py
  ✓ services/visibility.py без fastapi
  ⚠ routers/auth.py:65 session.commit — известная протечка
  ✓ sessionmaker только в db.py
  ✓ тег «Вход» есть в api.md
```

## 3. Слои

### 3.1 `routers/` — HTTP и ничего больше

**Отвечает за:** разбор запроса, коды ответов, `ETag`, `If-Match`,
`Idempotency-Key`, вызов сервиса, формирование схемы ответа.

**Нельзя:** писать SQL, открывать транзакцию, считать бизнес-правила.

Один файл на раздел [api.md §6](api.md), имена совпадают: `orders.py` — раздел
6.2, `shipping.py` — 6.3 и так далее. Тег в `APIRouter(tags=[...])` совпадает с
названием раздела: по нему сверяются счётчики в документации.

```python
router = APIRouter(tags=["Заказы"])

@router.post("/orders/{order_id}/accept", response_model=Order,
             summary="Принять заказ к сборке")
def accept(order_id: int, session: SessionDep,
           user=require(Section.ORDERS, edit=True),
           if_match: str = Header(alias="If-Match")):
    order = transitions.accept(session, order_id, user, version(if_match))
    return Order.of(order)
```

Версия из `If-Match` приходит в кавычках — `"7"`. Снимать их в одном месте, не в
каждом роутере.

**Готово, когда:** все операции раздела отвечают теми кодами, что обещает
[api.md](api.md), а в файле нет ни `session.commit()`, ни `update(`.

### 3.2 `schemas/` — форма данных

**Отвечает за:** то, что видит клиент. Имена полей обязаны совпадать с
[openapi.json](openapi.json) — иначе десктоп не разберёт ответ.

**Нельзя:** знать про ORM, ходить в базу, содержать правила.

Конструкторы `of()` собирают схему из модели. Они же — единственное место, где
живёт презентационная логика вроде сокращения ФИО:

```python
class UserBrief(Schema):
    id: int
    name: str            # «Кузнецов И.А.»

    @classmethod
    def of(cls, user):
        return cls(id=user.id, name=short_name(user.full_name))
```

Сокращает сервер, а не клиент: подпись под документом должна выглядеть одинаково
в приложении, в выгрузке и в письме.

Списки — всегда `Page[T]` из `common.py`: `items`, `total`, `limit`, `offset`.
Клиент читает ровно эти четыре поля и на их основе рисует пагинацию.

**Готово, когда:** `curl` отдаёт то же, что лежит в `openapi.json`, а
`check_docs.py` не находит расхождений.

### 3.3 `services/` — правила и транзакции

**Главный слой.** Здесь и только здесь начинается запись.

**Отвечает за:** три транзакции [api.md §7](api.md), выдачу штрихкода, фильтр
видимости, проверки переходов статусов.

**Нельзя:** знать про HTTP. Ни `fastapi`, ни `Request`, ни коды ответов. Сервис
получает сессию и бросает `ApiProblem` — превратить его в ответ дело `errors.py`.

Три транзакции лежат в одном файле `transitions.py` намеренно. «Резерв ставится»
и «резерв снимается весь» — две половины одного правила, и читать их надо рядом.
Разложи их по доменным пакетам, и первая же правка разъедется.

Границу транзакции задаёт сервис:

```python
def ship(session, order_id, user, version):
    with session.begin():
        ...            # проверки и запись целиком внутри
```

Оговорка, которая стоила отладки: `session.begin()` падает, если транзакция уже
открыта — а её открывает первый же `SELECT`. Поэтому либо `begin()` идёт до
любого чтения, либо запись фиксируется явным `commit()`. Второе — то, что сейчас
в `routers/auth.py`, и это **известная протечка слоя**: роутер там управляет
транзакцией. Причина не в лени: `consume_refresh` обязан зафиксировать отзыв
цепочки **до** `raise`, иначе откат уносит отзыв вместе с исключением, и защита
от кражи refresh не срабатывает ровно тогда, когда нужна. Этот баг был и
исправлен. Когда появится `transitions.py`, вход стоит переписать так же.

**Готово, когда:** транзакция проверяется тестом на голой сессии SQLAlchemy, без
запуска сервера и без токенов, и сбой посередине не оставляет ни движения, ни
статуса.

### 3.4 `deps.py` — кто пришёл и что можно

`current_user` разбирает `Authorization: Bearer`, достаёт пользователя, отвергает
удалённого и заблокированного. Блокировка действует сразу, не дожидаясь
истечения access-токена.

`require(section, edit=False)` — проверка по матрице `role_permission`. Права
читаются из базы на каждой проверке, а не едут в токене: админ снял галочку, и
это действует на следующем запросе, а не через пятнадцать минут.

> `require()` написан, но ни одним маршрутом ещё не вызывается — разделы, которым
> он нужен, не реализованы. Первым его получат заказы.

**Готово, когда:** `stockman` получает `403` на `/users`, а `manager` — `403` на
`POST /shipments/{id}/ship`.

### 3.5 `security.py` — пароли и токены

Argon2id, `check_needs_rehash` при входе. JWT на 15 минут с `{sub, wh, iat, exp}`
— ни прав, ни имени, ни роли: они меняются, а токен бы отставал.

Refresh — 32 случайных байта, в базе только SHA-256. Ротация при каждом
обновлении. Предъявление уже отозванного = признак кражи, гасится вся цепочка.

**Нельзя:** ходить в HTTP-слой, знать про роутеры.

### 3.6 `errors.py` — problem+json

Все отказы — RFC 9457. Клиент ветвится по `type` (стабильный URI), человеку
показывается `title`.

Три обработчика: свой `ApiProblem`, `RequestValidationError` → 422 с разбором по
полям, `HTTPException` → перевод. Последний важен: `detail` у маршрутизатора
английский («Not Found»), а клиент показывает `title` человеку как есть — в
русском интерфейсе это выглядело поломкой. Такой баг был.

**Нельзя:** выпускать наружу голый JSON. Ни одного ответа без `title` по-русски.

### 3.7 `db.py` и `settings.py`

`get_session` — сессия на запрос, транзакцию не открывает. `settings()` —
`pydantic-settings` с `lru_cache`, ни одного значения по умолчанию для секретов:
без `JWT_SECRET` короче 32 знаков приложение не поднимется.

### 3.8 `database/models.py`

Плоско, одним файлом, 16 таблиц. Источник правды для миграций.

`relationship` на схему не влияют — `alembic check` их не видит. Заведены для
API: без них каждый роутер собирал бы `JOIN` руками. **В списках подгружать
явно** через `selectinload`, иначе N+1 на каждой странице.

## 4. Как добавить раздел

По порядку, потому что каждый шаг опирается на предыдущий:

1. **Схемы.** `schemas/<раздел>.py`, имена полей сверить с `openapi.json`.
2. **Сервис**, если раздел пишет. Правила и транзакция. Тест на голой сессии —
   до всякого HTTP.
3. **Роутер.** `routers/<раздел>.py`, тег как в `api.md`, подключить в
   `main.py`.
4. **Права.** `require(Section.X)` на чтение, `require(Section.X, edit=True)` на
   запись.
5. **Сверка.** `check_layers.py` — правила слоёв. `check_docs.py` — счётчики,
   покрытие клиента, коды ошибок против живого сервера.
6. **Экран.** Открыть соответствующий экран приложения: он уже написан и ждёт
   этих эндпоинтов. Если экран не заполнился — контракт разошёлся.

Шаг 6 не формальность. Приложение перевели на API раньше сервера, и это вскрыло
семь несоответствий в контракте до того, как под них был написан код.

## 5. Тесты

**Их сейчас нет.** Всё, что описано ниже, — то, как должно быть; проверка пока
делается разовыми скриптами. Это главный незакрытый долг.

Каталог `backend/tests/`, `pytest`. До 8 августа `tests` стоял в `.gitignore` —
убрано, иначе в CI запускать нечего.

### 5.1 Слой сервисов — основное

Без сервера и без токенов. Сессия к тестовой базе, вызов функции, проверка
таблиц. Быстро, поэтому здесь и живёт большинство случаев.

```python
def test_ship_releases_whole_reserve(session, order):
    transitions.accept(session, order.id, manager, version=1)
    pack_box(session, order.id, "100512", qty=75, weight=120)
    transitions.ship(session, order.id, stockman, version=2)

    balance = session.get(StockBalance, (item.id, warehouse.id))
    assert balance.qty == 640.5 - 75      # списано упакованное
    assert balance.reserved == 0          # снят весь резерв, не только упакованное
```

Обязательные случаи — из [api.md §11](api.md):

- частичная отгрузка снимает весь резерв;
- приёмка приходует **принятое**, а не отгруженное;
- заказ в метрах проходит путь без округления;
- нехватка свободного остатка → `409`, ничего не записано;
- недопустимый переход статуса → `409`;
- сбой посередине не оставляет ни движения, ни статуса.

### 5.2 Слой HTTP

`TestClient` из FastAPI. Проверяются коды, заголовки и права — не бизнес-правила,
они уже проверены ниже.

- `If-Match` отсутствует → `428`, устаревший → `409`;
- `stockman` на `/users` → `403`;
- склад №4 не видит заказ между №1 и №3 — ни в списке, ни в карточке, ни в
  счётчиках на главной;
- повторный `POST /orders` с тем же `Idempotency-Key` не создаёт второй заказ;
- повторный `receive` того же штрихкода → `200`;
- каждый отказ — `application/problem+json` с русским `title`.

### 5.3 Правила слоёв

`check_layers.py`. Разбирает импорты через `ast`, ищет запрещённые вызовы,
сверяет теги роутеров с разделами `api.md` и что каждый роутер подключён в
`main.py`. Осознанные исключения — в `KNOWN_LEAKS` с причиной; исключение,
которое стало ненужным, проверка потребует удалить.

### 5.4 Документация против кода

`check_docs.py` сверяет `api.md` ↔ `openapi.json` ↔ клиент ↔ живой сервер:
счётчики по разделам против тегов схемы, покрытие клиента, поля JWT против
json-примера **в самом документе**, каждая строка таблицы ошибок против
фактического ответа. Расхождения между документом и кодом ловились именно так.

Это тоже должно переехать в `backend/tests/` и запускаться в CI.

### 5.5 Схема

`make check` — `alembic check`, схема не разошлась с моделями. Плюс обратимость:
`upgrade head → downgrade base → upgrade head` без ошибок.

## 6. Что считать готовым

| Слой | Критерий |
|---|---|
| `routers/` | коды как в api.md; ни `commit`, ни `update` в файле |
| `schemas/` | `curl` совпадает с `openapi.json`; `check_docs.py` чист |
| `services/` | транзакция проверена на голой сессии; сбой не оставляет следов |
| `deps.py` | `stockman` не открывает `/users` |
| `errors.py` | ни одного ответа без русского `title` |
| `models.py` | `make check` чист; в списках `selectinload` |
| слои | `check_layers.py` чист или протечка внесена в `KNOWN_LEAKS` |
| раздел целиком | соответствующий экран приложения заполнился живыми данными |

## 7. Известные долги

- Тестов нет; проверка разовыми скриптами.
- `routers/auth.py` управляет транзакцией — протечка слоя, см. 3.3.
- `require()` не вызывается ни одним маршрутом.
- `audit_log` и `idempotency_key` — таблицы есть, писателя нет. Эндпоинт
  `/users/{id}/activity` описан и реализован в клиенте, на сервере пуст.
- Две роли Postgres (`prozapas_owner` / `prozapas_app`) не заведены: API ходит
  под владельцем схемы, то есть с правом DDL.
- `alembic check` и обратимость миграций не в CI.
- Запросы к серверу из приложения синхронные: на медленной сети окно подмерзает.
