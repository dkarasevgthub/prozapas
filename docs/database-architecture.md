# Архитектура базы данных — техническое задание

Как устроен слой данных: состав таблиц, границы сервисов, инфраструктурный
пакет и стык с API.

Документ сводит принятые решения и заменяет собой ту часть
[database-spec_old.md](database-spec_old.md), которая описывает состав схемы. Расхождения
между ними разобраны в разделе 2 — спека писалась раньше, часть её решений
пересмотрена.

Смежные документы: [architecture.md](architecture.md) — общая картина и выбор
стека, [api.md](api.md) — эндпоинты.

---

## 1. Задача

Приложение ProЗапас держало все данные в одном файле `desktop/mock_data.json`.
Нужен сервер: PostgreSQL, API на FastAPI, десктоп переключается на HTTP вместо
чтения файла.

Состояние на 8 августа 2026: база поднята и промигрирована, десктоп переведён на
HTTP целиком, файла моков больше нет. Не написан сам API — он следующий.

Этот документ отвечает на три вопроса: **какие таблицы нужны**, **как код
разложен по границам** и **как процесс API соединяется с базой**.

## 2. Как есть сейчас

### 2.1 Что уже сделано

В `backend/database/` лежит одна миграция Alembic на 452 строки, создающая 21
таблицу с триггерами, частичными и GIN-индексами. Схема продумана: все
`ON DELETE` заданы явно, `CHECK`-ограничения на месте, `timestamptz` везде,
колонки `version` у изменяемых документов.

Поднимается Postgres 16 в Docker Compose.

### 2.2 Чего нет

**Моделей SQLAlchemy не существует.** В `alembic/env.py` стоит
`target_metadata = None`, поэтому автогенерация не работает и все последующие
миграции придётся писать руками. Ничто не проверяет, что схема в базе
соответствует ожиданиям кода.

**API не начат.** Из полусотни эндпоинтов не написано ничего.

**`seed.py` не запустится.** Он использует `Role` и `UserAccount`, которых нет,
импортов не содержит, пароль в строке подключения не совпадает с compose, а хеш
администратора — литерал `'$argon2id$...'`, с которым нельзя войти.

### 2.3 Дефекты, которые надо исправить

**Сломан путь к миграциям.** В `alembic.ini` указано
`script_location = %(here)s/alembic`, но сам файл лежит **внутри** `alembic/`.
Путь резолвится в несуществующий `alembic/alembic/`.

**`downgrade()` падает.** В `upgrade()` внешний ключ
`fk_warehouse_responsible_user` связывает `warehouse` → `user_account`, а в
`downgrade()` таблица `user_account` дропается раньше `warehouse`. Postgres
откажется: на неё ещё ссылаются. Нужен явный `drop_constraint` первой строкой.

**Коллация не задана.** В compose нет `POSTGRES_INITDB_ARGS`, кластер получает
умолчание образа. При этом `postgres:16-alpine` собран на musl, и glibc-локалей
в нём нет вообще — проверено, `locale -a` пуст, инициализация пишет
`WARNING: no usable system locales were found`. Сортировка ФИО и наименований
пойдёт по байтам: «Ёлкин» окажется после «Яблокова».

**`JSON` вместо `JSONB`** в `audit_log.before/after` и
`idempotency_key.response`. Тип `json` хранится текстом и переразбирается при
каждом чтении, индекс по нему не построить.

**Порт базы опубликован наружу.** В compose есть `ports: "5432:5432"` — Postgres
доступен с любой машины в сети склада, а пароль лежит рядом в том же файле в
git.

**Два индекса избыточны:** `order_position_order_idx` перекрыт
`UNIQUE (order_id, item_id)`, `receipt_scan_batch_idx` — `UNIQUE (batch_id,
barcode)`. Обе ведущие колонки уже проиндексированы.

### 2.4 Расхождения с функционалом приложения

Проверены все 13 экранов десктопа против схемы. Нашлось три несовпадения.

**Количества обязаны быть дробными.** Ручная операция в карточке товара
принимает `float` и печатает результат с двумя знаками для нештучных единиц
([product_detail.py](../desktop/app/pages/product_detail.py), метод
`_operation`). В справочнике есть позиции в метрах и листах. Схема объявляет
`qty` целым — это ломает уже существующую функцию.

**Нет колонки `login`.** Форма заведения сотрудника спрашивает логин отдельным
полем ([users.py](../desktop/app/pages/users.py), метод создания), подставляя
часть адреса почты лишь как значение по умолчанию. В `user_account` есть только
`email`.

**Списание и корректировка ссылаются на несуществующие документы.** История в
карточке товара показывает колонку «Документ» со значениями «Списание №1234»,
«Инвентаризация №1187». В схеме `stock_movement.doc_type` / `doc_id` указывают
на документ, но таблиц под списание и инвентаризацию нет — только
`receipt_batch` и `shipment`.

## 3. Как должно быть

### 3.1 Состав данных — 19 таблиц

```
catalog     warehouse · supplier · catalog_item                          3
accounts    role · user_account · role_permission · refresh_token        4
inventory   stock_balance · stock_movement                               2
orders      sales_order · order_position · order_status_event            3
shipping    shipment · shipment_box                                      2
receiving   receipt_batch · receipt_batch_position · receipt_scan        3
инфра       audit_log · idempotency_key                                  2
                                                                        ──
                                                                        19
```

Четырнадцать таблиц выводятся прямо из экранов приложения. Остальные пять — из
требований: журнал движений нужен, чтобы баланс можно было сверить и объяснить;
`refresh_token` — для сессий API; `audit_log` и `idempotency_key` —
инфраструктура.

### 3.2 Изменения относительно текущей миграции

**Убираются две таблицы.**

`print_job` — единственное, ради чего она заводилась, это правило «перепечать не
создаёт вторую коробку». Оно и так держится: коробка живёт в `shipment_box`,
перепечать её не трогает, а факт печати есть в `shipment_box.printed_at`.
Осознанная потеря: «сколько раз печатали эту этикетку» ответа не имеет.

`label_template` — без журнала печати ссылаться на версию шаблона неоткуда, а
сам макет собирается в клиенте
([shipping.py](../desktop/app/pages/shipping.py), метод `_label_zpl`). Если
позже понадобится менять макет без пересборки приложения, таблица возвращается
отдельной миграцией.

**`receipt_scan` меняет природу.** Это больше не журнал, а рабочая таблица со
временем жизни партии. Уходят вычисляемые `diff_kg`, `diff_percent` и
дублирующий `expected_weight` (он есть в позиции партии). Остаётся главное —
`UNIQUE (batch_id, barcode)`.

Пока партия в работе, правда — строки сканов: по ним считается прогресс
«принято 2 из 4» и отсекается повторный скан. При завершении приёмки строки
сворачиваются в агрегат и удаляются. Один источник правды в каждый момент,
инкрементных счётчиков нет.

**`receipt_batch_position` получает три колонки:** `accepted_boxes`,
`actual_weight`, `missing_boxes`. Это итог приёмки — основание для претензии
поставщику, он переживает партию.

Свёртка и оприходование идут одной транзакцией, поэтому «свернуть наполовину»
невозможно:

```sql
BEGIN;
  UPDATE receipt_batch_position SET accepted_boxes = …, actual_weight = …,
                                    missing_boxes = …
    FROM (SELECT item_id, count(*), sum(actual_weight),
                 count(*) FILTER (WHERE is_missing)
            FROM receipt_scan WHERE batch_id = :id GROUP BY item_id) agg …;
  INSERT INTO stock_movement …;
  UPDATE stock_balance SET qty = qty + … WHERE … AND version = :v;
  UPDATE receipt_batch SET status = 'done', accepted_at = now();
  DELETE FROM receipt_scan WHERE batch_id = :id;
COMMIT;
```

Страховка от ошибки в агрегирующем запросе: `audit_log` в этой же транзакции
пишет полный список сканов в поле `after`. Детализация сохраняется в журнале
аудита, а не в растущей рабочей таблице.

**Количества становятся дробными.** `Numeric(12,3)` для `stock_balance.qty`,
`reserved`, `min_qty`, `order_position.qty`, `shipment_box.qty`,
`stock_movement.delta`, `balance_after`. Число коробок (`receipt_batch_position.
boxes`) остаётся целым.

**Добавляется `user_account.login`** — `NOT NULL`, с уникальным индексом по
`lower(login) WHERE deleted_at IS NULL`, как у почты.

**Списание и корректировка обходятся без документа.** `doc_type` и `doc_id`
остаются `NULL` (они уже допускают это), в колонке «Документ» показывается
`comment`. Форма операции спрашивает именно комментарий, а не номер. Если
бухгалтерии понадобятся нумерованные акты — это отдельная задача с печатной
формой, а не колонка.

**Прочее:** `JSON` → `JSONB`; `bigserial` → `Identity()`; единый механизм мягкого
удаления `deleted_at` вместо трёх (`is_archived`, `is_active`, `deleted_at`);
`CHECK`-перечисления собираются из `StrEnum`; поисковый `tsvector` становится
`Computed`-колонкой вместо функционального индекса; два избыточных индекса
удаляются.

**Переименование `order` → `sales_order`.** Зарезервированное слово тянет за
собой кавычки в каждом запросе, `EXPLAIN` и ручной выборке — навсегда.

### 3.3 Сервисы

Шесть доменных сервисов, а не восемь из [architecture.md](architecture.md):
`labeling` исчез вместе со своими таблицами, выдача штрихкода коробки —
функция `shipping`; `dashboard` своих таблиц не имеет и остаётся фасадом на
чтение в слое API.

```
             ┌─ orders ─┐   ┌─ shipping ─┐   ┌─ receiving ─┐
             └────┬─────┘   └─────┬──────┘   └──────┬──────┘
                  └───────────────┼─────────────────┘
                          ┌───────▼────────┐
                          │   inventory    │
                          └───────┬────────┘
                          ┌───────▼────────┐
                          │    catalog     │
                          └────────────────┘
                    accounts — сбоку, никого не зовёт
```

Структура каждого одинакова:

```
api.py         HTTP, Pydantic, коды ответов. Транзакций не открывает.
service.py     Правила и границы транзакции.
repository.py  Запросы к своим таблицам. Сессию получает, не создаёт.
models.py      Таблицы этого сервиса.
```

**Модели живут внутри сервиса, а не в общем пакете.** Это принципиально: общий
пакет делает импорт чужой модели легальным, и первый же удобный `JOIN` через
границу стирает её. Когда модели лежат по сервисам, нарушение видно в шапке
файла на ревью.

### 3.4 Пакет `db/` — инфраструктура

```
backend/db/
├── alembic.ini              # снаружи alembic/, иначе script_location ломается
├── Dockerfile
├── Makefile
├── requirements.txt         # sqlalchemy, alembic, psycopg — без FastAPI
├── base.py                  # Base, naming_convention, миксины
├── types.py                 # QTY = Numeric(12,3), Weight
├── enums.py                 # StrEnum + сборка CHECK
├── session.py               # engine, sessionmaker, get_session
├── models.py                # audit_log, idempotency_key
├── registry.py              # импортирует модели всех сервисов
└── alembic/{env.py, versions/}
```

Ни одного запроса к данным и ни одного бизнес-правила. Своих таблиц две, обе
сквозные: их пишет middleware, а не домен.

`registry.py` — единственное место, знающее про все домены сразу. Существует
ради `target_metadata` и больше нигде не используется. Зависимость в одну
сторону: сервисы знают про `db/`, `db/` про сервисы — только здесь.

**Соглашение об именах** задаётся в `Base.metadata` **до первой ревизии**:

```python
convention = {
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s",
    "pk": "pk_%(table_name)s",
}
```

Без него автогенерация плодит ограничения с именами от Postgres, и в
`downgrade` их нечем адресовать. Позже это отдельная миграция с переименованием
всего.

**Миксины:** `PkMixin` (`Identity`), `TimestampMixin`, `SoftDeleteMixin`,
`VersionMixin` (`version_id_col` — подмешивается к `sales_order`, `shipment`,
`stock_balance`, `receipt_batch`).

**`updated_at` — через ORM, без триггеров:**

```python
class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(
        server_default=func.now(), onupdate=func.now()
    )
```

Триггеров в схеме не остаётся вовсе. Причина: Alembic их не видит, поэтому
каждая новая таблица требовала бы ручной дописки в сгенерированный файл — ровно
та щель, через которую расходятся схема и код. Плата: `UPDATE` из psql мимо ORM
не обновит колонку. Все записи идут через один сервер и один ORM, так что это
приемлемо.

### 3.5 Правило транзакции

> Транзакцию открывает только тот сервис, которого позвал API. Вложенные сервисы
> её не открывают — они получают сессию и работают в чужой транзакции.

```python
# orders/service.py — верхний уровень
def accept(session, order_id, user, if_match):
    with session.begin():
        order = repo.get(session, order_id)
        if order.version != if_match:
            raise Conflict()
        inventory.reserve(session, order.positions, order.owner_warehouse_id)
        order.status = OrderStatus.PROCESSING
        repo.add_status_event(session, order, OrderStatus.PROCESSING, user)

# inventory/service.py — вложенный, session.begin() не зовёт:
# SQLAlchemy бросит "a transaction is already begun"
```

`session.commit()` не вызывается нигде — коммитит `with session.begin()` на
выходе из верхнего уровня, один раз. Именно это делает «принять заказ и
зарезервировать остаток» одной транзакцией, ради чего и выбирался монолит.

### 3.6 Чужие данные — вызов, а не JOIN

Экран «Остатки» показывает наименование и единицу (`catalog`) рядом с
количеством и резервом (`inventory`). Соблазн — `JOIN` на `catalog_item`; как
только он появился, граница исчезла.

Правильно — два запроса, второй пакетом:

```python
balances, total = inventory.list_balances(session, limit=limit, offset=offset)
items = catalog.get_many(session, [b.item_id for b in balances])
```

Ключевое — `get_many`, а не `get` в цикле: один лишний запрос на страницу, а не
пятьдесят.

### 3.7 Стык API ↔ база

```
десктоп ──HTTPS/JSON──▶ api (uvicorn)                    db (postgres)
                          │  SQLAlchemy Engine               │
                          │  пул 10 соединений ──────TCP─────┘
                          │  роль prozapas_app          внутренняя сеть compose,
                          └─ сессия на запрос           порт наружу не публикуется
```

**Синхронный SQLAlchemy, не асинхронный.** Асинхронный требует `await` в каждом
запросе, запрещает ленивую подгрузку связей и даёт непрозрачные ошибки про
greenlet; окупается он при сотнях одновременных запросов. При двадцати
пользователях берутся обычные `def`-эндпоинты — FastAPI сам уводит их в пул
потоков.

**Драйвер `psycopg` (версия 3)**, не `psycopg2`.

```python
engine = create_engine(
    os.environ["DATABASE_URL"],
    pool_size=10, max_overflow=10,
    pool_pre_ping=True,      # без этого после перезапуска БД пойдут 500-е
    pool_recycle=1800,
)

def get_session() -> Iterator[Session]:
    with SessionLocal() as session:
        yield session
```

`expire_on_commit=False` в `sessionmaker` — иначе после коммита обращение к полю
объекта уходит в базу заново и в схему ответа прилетает `DetachedInstanceError`.

Сессия живёт ровно один запрос. Соединение берётся из пула при первом
обращении к базе и возвращается на выходе из эндпоинта.

Пул принадлежит процессу: при нескольких воркерах uvicorn у каждого свой. Для
этой нагрузки достаточно одного-двух воркеров.

**Ошибки базы → HTTP**, всё в `application/problem+json`:

| Исключение | Ответ | Когда |
|---|---|---|
| `StaleDataError` | `409` | версия разошлась, документ уже изменили |
| `IntegrityError` на `UNIQUE (batch_id, barcode)` | `200` с существующей строкой | повторный скан — это и есть идемпотентность |
| `IntegrityError` на уникальном номере | `409` | дубль номера заказа |
| `IntegrityError` на `CHECK` | `422` | попытка увести остаток в минус |
| `DBAPIError`, таймаут | `503` | база недоступна |

Ретраев на стороне API нет. Повторяет клиент, и только идемпотентные операции.

**Идемпотентность** нужна только на создание заказа. Для скана и коробки её
бесплатно даёт естественный ключ: `UNIQUE (batch_id, barcode)` и
`shipment_box.barcode`.

### 3.8 Эксплуатация

**Две роли в БД.** `prozapas_owner` владеет схемой, под ним ходит только
`migrate`. `prozapas_app` имеет лишь DML, без DDL — под ним работает API.
Приложению `DROP TABLE` не нужен никогда.

**Миграции запускает отдельный сервис**, не API: при двух воркерах их запустили
бы двое одновременно.

```yaml
  db:
    environment:
      POSTGRES_INITDB_ARGS: "--locale-provider=icu --icu-locale=ru-RU --encoding=UTF8"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U prozapas_user -d prozapas_db"]
    # ports наружу не публикуются; для отладки — "127.0.0.1:5432:5432"

  migrate:
    command: alembic upgrade head
    depends_on: { db: { condition: service_healthy } }

  api:
    depends_on: { migrate: { condition: service_completed_successfully } }
```

Коллация задаётся **на initdb**. Поменять её потом можно только пересозданием
кластера, поэтому сделать это нужно до первых данных. ICU-провайдер работает на
alpine-образе (библиотеки в нём есть), менять образ на Debian не требуется.
Оговорка: при смене мажорной версии ICU правила сортировки меняются, и
текстовые индексы требуют `REINDEX`. Postgres об этом предупредит; образ стоит
обновлять осознанно.

**Регламент:** `pg_dump` ежедневно с копией на отдельный носитель, ежемесячная
проверка восстановления, чистка `idempotency_key` старше суток и просроченных
`refresh_token`, алерт на неудачный бэкап и на место на диске.

### 4.1 Про перенос данных

Два места требуют явного правила, иначе перенос молча исказит данные.

**Резерв и минимальный остаток сейчас на товар, а в схеме — на пару
товар-склад.** В JSON `reserved` и `minQty` лежат на артикуле целиком. Это не
копирование, а размазывание: 300 зарезервированных болтов надо как-то разложить
по двум складам.

**Журнал движений пуст.** Переносить в него нечего — истории в JSON нет. После
импорта сверочный запрос «сумма движений = баланс» не сойдётся, пока на каждый
остаток не будет заведено стартовое движение типа `recount`.

## 5. Осознанно отложено

- **Несколько своих складов.** Флаг `warehouse.is_own` есть, но заказ хранит
  только склад-контрагента, а направление считается относительно единственного
  своего склада. Понадобится второй — нужна колонка `sales_order.
  owner_warehouse_id` и тип движения `transfer`.
- **`ck_role_code`.** Ограничение `code IN ('manager','stockman','admin')` на
  таблице `role` противоречиво: содержимое таблицы зафиксировано проверкой.
  Новая роль потребует миграции, хотя матрица прав в приложении рисуется по
  строкам таблицы и к новым ролям готова. Убрать, когда дойдут руки до ролей.
- **Адресное хранение** (зоны, стеллажи, ячейки) — третья размерность в
  остатках, движениях и резервировании. Отдельный проект; журнал движений
  позволяет перейти на него в любой момент.
- **Права по складам.** `role_permission` — это роль × раздел, измерения склада
  в нём нет. Чтобы не переделывать потом всё разом, репозитории с самого начала
  принимают `warehouse_id` в фильтрах.
- **Секционирование `audit_log`**, репликация, PgBouncer — по факту роста.

## 6. Открытые вопросы

1. **Сколько складов реально?** Если один — раздел 5 можно не открывать вовсе.
2. **Нужен ли обмен с 1С?** От этого зависит, становится ли `code1c` ключом
   интеграции (тогда `NOT NULL UNIQUE` и эндпоинты выгрузки) или остаётся
   справочным полем.
3. **Нужна ли работа офлайн?** Это очередь операций на клиенте и заметно больше
   кода. Сервер стоит на том же складе, поэтому предлагается не делать.

## 7. Критерии приёмки

- [ ] Модели — источник правды: `alembic check` на чистом дереве не находит
      расхождений.
- [ ] Первая ревизия сгенерирована автоматически и создаёт схему на чистой базе.
- [ ] `upgrade head → downgrade base → upgrade head` проходит без ошибок.
- [x] Порт базы опубликован только на петлю. API ходит под ролью без DDL — нет.
- [x] `seed.py` наполняет базу для тестовых прогонов: роли, права, склады,
      21 учётная запись, номенклатура, остатки. Повторный запуск ничего не
      дублирует. Пароль у всех один, из `SEED_PASSWORD` — это стенд, не прод.
- [x] Заказов сид не создаёт: резерв и движения — следствие трёх транзакций из
      [api.md §7](api.md), и вторая их копия в сиде разошлась бы с первой.
      Демо-заказы завести через API и тогда же проверить «сумма движений =
      баланс».
- [ ] Сид под рабочий контур: только роли, права и один администратор. Склады
      и номенклатуру там заводят руками — выдуманные названия на прод не везут.
- [ ] Ограничения покрыты тестами, включая отрицательные сценарии: списание в
      минус, двойной скан, дубль штрихкода, `reserved > qty`.
- [ ] Дробные количества проходят весь путь: заказ в метрах создаётся,
      отгружается и списывается без округления.
- [ ] `EXPLAIN` на списках заказов, остатков и справочника показывает
      использование индексов.
