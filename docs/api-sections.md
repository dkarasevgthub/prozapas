# Разделы API — задания на реализацию

Восемь разделов, 46 операций. По каждому: что уже есть, что должно работать,
чем проверять и что считать сделанным.

Раздел можно брать целиком и делать независимо от остальных — порядок в
документе рекомендательный, зависимости указаны явно.

Контракт полей и кодов — [api.md](api.md), устройство кода —
[api-architecture.md](api-architecture.md), схема — [database-architecture.md](database-architecture.md).

Состояние на 8 августа 2026:

| Раздел | Операций | Готово | Экран приложения |
|---|---|---|---|
| [Служебные](#1-служебные--4) | 4 | ✔ все | главная |
| [Вход](#2-вход--4) | 4 | ✔ все | вход |
| [Заказы](#3-заказы--7) | 7 | — | заказы, карточка, новый заказ |
| [Отгрузка](#4-отгрузка--5) | 5 | — | отгрузка |
| [Приёмка](#5-приёмка--5) | 5 | — | приёмка |
| [Остатки](#6-остатки--5) | 5 | — | остатки, карточка товара |
| [Справочник](#7-справочник--5) | 5 | — | справочник |
| [Пользователи](#8-пользователи-и-права--11) | 11 | — | пользователи, карточка |

**Все экраны приложения уже написаны и ждут эндпоинтов.** Это и есть главная
приёмка: дописал раздел — открой экран, он должен заполниться. Не заполнился —
контракт разошёлся, и правится он, а не экран.

Три операции экранами не проверяются, у них нет потребителя в интерфейсе:

| Операция | Кто зовёт |
|---|---|
| `GET /health` | `api.available()` — индикатор связи |
| `GET /version` | никто, пригодится диагностике |
| `POST /catalog/{id}/archive` | никто: в справочнике нет кнопки «Архивировать» |

Последнее — незакрытая работа на стороне приложения, не сервера. Эндпоинт делать
надо, но проверять его придётся `curl`-ом.

**Общее для всех разделов**, повторять в каждом не буду:

- Склад берётся из токена, `warehouse_id` в запросах не принимается никогда.
- Список отдаёт `{items, total, limit, offset}`, `limit` по умолчанию 50, макс 200.
- Отказ — `application/problem+json` с русским `title`.
- Изменение документа требует `If-Match`; нет — `428`, устарел — `409`.
- Права проверяются `require(Section.X)` на чтение, `require(Section.X, edit=True)`
  на запись.
- Чужой документ отдаёт `404`, а не `403`.

## 1. Служебные — 4

```
GET /health      GET /version      GET /bootstrap      GET /dashboard
```

**Готово целиком.** `routers/service.py`, 120 строк.

Что важно знать, если будете трогать:

`/bootstrap` отдаёт склады, роли, разделы, права, себя и **список сотрудников**.
Сотрудники именно здесь, а не в `/users`: тот открыт только администратору, а
фильтр «Ответственный» нужен всем. Имя — целиком, не сокращённое: это выпадающий
список, там читают глазами.

`/dashboard` считает по своему складу. «К отгрузке» — входящие в работе, то есть
у нас заказали и мы собираем. «К приёмке» — исходящие в пути. Пока заказов нет,
все счётчики нули, и это правильный ответ, а не заглушка.

## 2. Вход — 4

```
POST /auth/login    POST /auth/refresh    POST /auth/logout    GET /auth/me
```

**Готово целиком.** `routers/auth.py` + `security.py`.

Три решения, которые легко случайно отменить:

- **Прав в токене нет.** Читаются из `role_permission` на каждой проверке. Иначе
  админ снимает галочку, а действует это через 15 минут.
- **Выход не требует access-токена.** Приложение простояло ночь, access истёк,
  человек жмёт «Выйти» — должно сработать.
- **Отзыв цепочки фиксируется до `raise`.** Иначе откат уносит отзыв вместе с
  исключением, и защита от кражи refresh не работает ровно тогда, когда нужна.
  Это был баг, см. [api-architecture.md §3.3](api-architecture.md).

## 3. Заказы — 7

```
GET  /orders                  список, вкладки incoming/outgoing
POST /orders                  создать, Idempotency-Key обязателен
GET  /orders/{id}             карточка, ETag
GET  /orders/{id}/history     лента статусов
POST /orders/{id}/accept      принять к сборке   ← транзакция №1
POST /orders/{id}/decline     отклонить
POST /orders/{id}/cancel      отменить
```

**Есть:** `services/visibility.py` — фильтр `from_warehouse_id = мой OR
to_warehouse_id = мой` плюс `outgoing()` и `incoming()`. Написан, нигде не
вызывается.

**Зависимости:** нет. Берётся первым — от него зависят отгрузка и приёмка.

### Что должно работать

**Направление не хранится.** `tab=outgoing` — `to_warehouse_id` мой, мы заказали
и примем. `tab=incoming` — `from_warehouse_id` мой, у нас заказали и мы отгружаем.
Одна запись, два взгляда.

**Фильтры списка:** `status` (можно несколько), `warehouse_id` (второй склад),
`responsible_id`, `created_from`, `created_to`, `q` (префикс номера).

**Создание:** склад-заказчик — свой, из токена; в теле только
`from_warehouse_id`, позиции и комментарий. Номер выдаёт сервер из
`order_number_seq`. Наличие на чужом складе **не проверяется** — отправитель сам
решит, сможет ли собрать. `Idempotency-Key` обязателен: у заказа нет
естественного ключа, и повтор из-за таймаута создал бы дубль.

Позиции в ответе обогащаются: клиент прислал артикул и количество, наименование
и единицу подставляет справочник.

**Переходы:**

```
created ──▶ processing ──▶ shipped ──▶ received
   │             │
   ▼             ▼
declined     cancelled
```

`accept` и `decline` — только отправитель, только из `created`. `cancel` — только
заказчик и только пока нет ни одной коробки. Всё остальное → `409`.

**Транзакция №1 «принять заказ»** ([api.md §7.1](api.md)):

```
проверки:  version совпал · статус created · мы отправитель
           свободный остаток >= заказанного по каждой позиции
──────────────────────────────────────────────────────────
reserved += qty по каждой позиции
движение reserve
order.status = processing
событие статуса
создаётся пустая отгрузка
```

Нехватка остатка → `409` с перечнем позиций: артикул, сколько просят, сколько
свободно. Клиент это показывает.

### Как тестить

На голой сессии, без HTTP:

- принять заказ → `reserved` вырос, `qty` не тронут;
- принять при нехватке → `409`, в базе не изменилось **ничего**;
- принять дважды → второй раз `409 invalid_transition`;
- отменить после первой коробки → `409`;
- отклонить чужой заказ (мы заказчик, не отправитель) → `409`.

Через `TestClient`:

- склад №4 не видит заказ между №1 и №3: ни в `/orders`, ни в `/orders/{id}`
  (там `404`), ни в счётчиках `/dashboard`;
- `accept` без `If-Match` → `428`, с устаревшим → `409`;
- повторный `POST /orders` с тем же `Idempotency-Key` → тот же заказ, не второй;
- `manager` создаёт заказ, `stockman` — `403`.

### Результат

Экран «Заказы» показывает обе вкладки с фильтрами и серверной пагинацией.
Карточка заказа открывается, кнопки «Принять» / «Отклонить» / «Отменить» видны по
роли и статусу, конфликт версий перечитывает карточку. «Новый заказ» создаёт заказ
и переходит на его карточку. На главной счётчики перестают быть нулями.

## 4. Отгрузка — 5

```
GET    /shipments                                список
GET    /shipments/{order_id}                     карточка: to_pack + boxes
POST   /shipments/{order_id}/boxes               упаковать коробку
DELETE /shipments/{order_id}/boxes/{box_id}      удалить коробку
POST   /shipments/{order_id}/ship                отгрузить   ← транзакция №2
```

**Зависимости:** заказы. Отгрузка живёт только у заказа в `processing`.

**Обратная зависимость:** карточка заказа зовёт `GET /shipments/{order_id}` —
панель прогресса сборки показывается прямо там. То есть без этого раздела карточка
заказа будет наполовину пустой, хотя формально раздел «Заказы» готов.

### Что должно работать

Виден только тот заказ, где **мы отправитель** — `incoming` в терминах вкладок.

**Карточка** отдаёт `to_pack` и `boxes`. `to_pack` по позиции: `ordered`,
`packed`, `remaining`, `unit`, `unit_weight`. Считает сервер, клиент не вычитает.

**Штрихкод выдаёт сервер** при создании коробки ([api.md §8.1](api.md)):

```
WH{id склада-заказчика, 3 знака}{номер заказа}{артикул}        первая
WH{...}-02                                                     вторая
WH{...}-03                                                     третья
```

`NN` считается **внутри артикула**, а не по всем коробкам отгрузки. Первая
суффикса не получает никогда — иначе пришлось бы переклеивать наклеенную
этикетку. Id склада дополняется до трёх знаков: без этого «склад 1, заказ 22001»
и «склад 12, заказ 2001» дают одну строку.

В теле создания — только `article`, `qty`, `weight`. Штрихкода в запросе нет.

**Отметки о печати нет.** Этикетка печатается сразу после создания коробки, минуя
API. Не вышла — клиент удаляет коробку. Значит существующая коробка всегда
напечатана.

**Транзакция №2 «отгрузить»** ([api.md §7.2](api.md)):

```
проверки:  version совпал · есть хотя бы одна коробка · мы отправитель
──────────────────────────────────────────────────────────
qty      -= упаковано
reserved -= заказано          ← весь резерв, не только упакованное
движение shipment на упакованное
shipment.status = done, shipped_at
order.status = shipped, shipped_at
событие статуса
```

**Резерв снимается полностью.** Второй отгрузки по заказу не будет, разница
возвращается в свободный остаток. Это главное правило раздела, и его легко
сделать неправильно.

Ответ несёт `shortage` — позиции с `remaining > 0`. Клиент по нему предупреждает
о частичной отгрузке.

### Как тестить

На голой сессии:

- упаковать три коробки одного артикула → штрихкоды без суффикса, `-02`, `-03`;
- упаковать два разных артикула → у каждого своя нумерация с нуля;
- склад 1 заказ 22001 и склад 12 заказ 2001 → **разные** штрихкоды;
- частичная отгрузка: заказано 100, упаковано 75 → `qty -= 75`, `reserved -= 100`,
  свободный остаток вырос на 25;
- отгрузить без коробок → `409`;
- удалить коробку → `packed` уменьшился, `remaining` вырос.

Через `TestClient`:

- `ship` без `If-Match` → `428`;
- два кладовщика отгружают один заказ: второй получает `409`;
- `manager` на `ship` → `403`.

### Результат

Экран «Отгрузка» показывает список с прогрессом «1 из 2». Карточка позволяет
выбрать позицию, взвесить, создать коробку — штрихкод приходит с сервера и уходит
в этикетку. Кнопка «Отгрузить» неактивна, пока не собрано всё; при частичной
отгрузке спрашивает подтверждение с перечнем недостающего.

## 5. Приёмка — 5

```
GET    /receipts                                      список
GET    /receipts/{order_id}                           карточка: boxes отправителя
POST   /receipts/{order_id}/boxes/{barcode}/receive   отметить принятой
DELETE /receipts/{order_id}/boxes/{barcode}/receive   отменить скан
POST   /receipts/{order_id}/complete                  завершить  ← транзакция №3
```

**Зависимости:** отгрузка. Принимать можно только отгруженное.

### Что должно работать

Виден только заказ, где **мы заказчик** и статус `shipped` или `received`.

**Коробки настоящие.** Карточка отдаёт те `shipment_box`, что упаковал
отправитель, со его штрихкодами и весами. Ничего не синтезируется: в старой
версии приёмка выдумывала ожидаемые коробки, и они не могли совпасть с
упакованным.

**Расхождение считает сервер.** Клиент присылает только `actual_weight`, в ответ
получает `diff_kg` и `diff_percent`. Разность не хранится — вычисляется из
`actual_weight − weight`.

**Идемпотентность по штрихкоду.** Повторный `receive` того же штрихкода → `200` с
той же коробкой, не ошибка. `Idempotency-Key` не нужен: штрихкод и есть
естественный ключ.

**Транзакция №3 «завершить приёмку»** ([api.md §7.3](api.md)):

```
проверки:  version совпал · статус приёмки progress · мы получатель
──────────────────────────────────────────────────────────
qty += сумма по принятым коробкам   ← принятым, не отгруженным
движение receipt
receipt.status = done, accepted_at
order.status = received, accepted_at
событие статуса
```

**Приходуется принятое, а не отгруженное.** Непринятые коробки остаются без
`received_at` — это и есть недостача, отдельного поля под неё нет. Ответ несёт
`missing` с их перечнем.

Заказ принимают даже с расхождением: недостача не блокирует завершение.

### Как тестить

На голой сессии:

- принять 2 коробки из 3, завершить → `qty` вырос на сумму **двух**, третья без
  `received_at`;
- повторный `receive` того же штрихкода → та же коробка, `200`, не дубль;
- отмена скана → `received_at` сброшен, коробка вернулась в очередь;
- завершить, когда не принято ничего → приход нулевой, статус `received`;
- чужой штрихкод → `404`.

Сквозной, самый ценный: заказ проходит оба склада, и **штрихкоды, которые
сгенерировала отгрузка, сканирует приёмка**. Баланс должен сойтись: у отправителя
списано упакованное, у получателя оприходовано принятое, разница — недостача.

### Результат

Экран «Приёмка» показывает прогресс по коробкам «0 из 3». Первый скан выбирает
коробку, второй фиксирует вес с весов и получает расхождение с сервера. Чужой
штрихкод даёт предупреждение. Завершение спрашивает подтверждение с перечнем
непринятых.

## 6. Остатки — 5

```
GET  /stock                        список, in_stock по умолчанию true
GET  /stock/summary                четыре карточки экрана
GET  /stock/{item_id}              разбивка по складам
GET  /stock/{item_id}/movements    история движений
POST /stock/operations             ручная операция
```

**Зависимости:** справочник (для наименований). Может делаться параллельно
заказам — на них не влияет.

### Что должно работать

**`in_stock` по умолчанию `true`:** экран «Остатки» показывает то, что лежит на
складе, а не всю номенклатуру. Вместе с `below_min=true` его надо снимать —
позиция, которой ноль при минимуме пятьдесят, как раз и требует дозаказа.

**`by_warehouse`** — разбивка по складам, нужна экрану «Новый заказ» в режиме
«найти где есть»: он предлагает склад с наибольшим остатком, остальные раскрывает
дочерними строками. Название склада не дублируется, клиент берёт его из
`/bootstrap`.

**Свободный остаток не хранится:** `free = qty − reserved`, считается на чтении.

**Ручная операция.** Типы `receipt`, `shipment`, `writeoff`, `recount`. Для
`recount` `qty` — **новое значение остатка, а не дельта**. У списания и
корректировки документа нет: `doc_type` и `doc_id` пустые, в истории показывается
`comment`. Проверка «не списать больше, чем есть» — на сервере: только он знает
остаток на момент операции.

`reserve` и `unreserve` вручную не проводятся — их ставит заказ.

### Как тестить

- `recount` на 500 при остатке 640.5 → остаток стал 500, движение с дельтой
  −140.5;
- `writeoff` больше остатка → `409`, ничего не записано;
- дробные: заказ в метрах проходит путь без округления, `Numeric(12,3)`;
- `below_min=true` вместе с `in_stock=false` возвращает позиции с нулём;
- сумма движений по позиции = текущий баланс (сверочный запрос).

### Результат

Экран «Остатки» показывает список с поиском и серверной пагинацией, четыре
карточки сверху. Карточка товара показывает остаток на своём складе цифрами,
чужие — строкой, историю движений с фильтром по типу и позволяет провести
операцию.

## 7. Справочник — 5

```
GET   /catalog                 список, поиск по search_vector
POST  /catalog                 добавить
GET   /catalog/{id}            карточка
PATCH /catalog/{id}            изменить
POST  /catalog/{id}/archive    архивировать
```

**Зависимости:** нет. Самый простой раздел, годится как первый.

### Что должно работать

Поиск `q` идёт по генерируемой колонке `search_vector` — наименование, артикул,
код 1С, GIN-индекс, русский словарь. Не `LIKE`.

Артикул и код 1С уникальны. Занятый артикул → `409` с внятным `title`: клиент
показывает его прямо в форме, чтобы человек поправил и отправил снова.

**Позиция с движениями не удаляется, а архивируется.** Архивная не появляется в
поиске и в «Новом заказе», но остаётся в истории движений и в старых заказах.

`unit_weight` дробный: шайба весит 0.005 кг, до копеек не округлить.

### Как тестить

- поиск по части наименования, по артикулу, по коду 1С — все три находят;
- поиск «труба» находит «Труба стальная» (русский словарь, регистр);
- создать с занятым артикулом → `409`;
- архивировать → исчезла из `/catalog`, осталась в `/stock/{id}/movements`;
- `unit_weight = 0.005` возвращается как `0.005`, не `0.01`.

### Результат

Экран «Справочник» показывает список с поиском, кнопка «Добавить позицию»
создаёт, занятый артикул показывается в форме. Клик открывает карточку товара.

## 8. Пользователи и права — 11

```
GET    /users                  список с фильтрами
POST   /users                  завести
GET    /users/{id}             карточка
PATCH  /users/{id}             изменить
DELETE /users/{id}             мягкое удаление
POST   /users/{id}/block       заблокировать
POST   /users/{id}/unblock     разблокировать
POST   /users/{id}/password    сменить пароль
GET    /users/{id}/activity    история действий из audit_log
GET    /permissions            матрица прав
PUT    /permissions            изменить матрицу
```

**Зависимости:** нет. Но `require()` из `deps.py` впервые заработает здесь или в
заказах — смотря что сделают раньше.

### Что должно работать

Раздел доступен **только администратору**: `users` в матрице у `manager` и
`stockman` — нет доступа.

**Логин и почта уникальны среди неудалённых** — частичные unique-индексы
`ix_user_account_login` и `ix_user_account_email` с `WHERE deleted_at IS NULL`.
Занятость проверяет сервер: только у него весь список, включая тех, кого экран
сейчас не показывает.

`DELETE` — **мягкое удаление**, `deleted_at`. Подписи под заказами и движениями
остаются: `user_id` там `ON DELETE SET NULL`, но при мягком удалении и он цел.

**Пароль приходит открытым, хэширует сервер.** Клиент argon2 не считает и не
должен. Минимальная длина проверяется на обеих сторонах.

**Правила, которым нужен сам объект** — в сервисе, не на маршруте: нельзя
заблокировать или удалить себя, изменить свою роль, заблокировать последнего
администратора.

**Матрица прав** уходит и приходит целиком: полтора десятка строк, а частичное
обновление потребовало бы ключа на каждую клетку. `can_edit` без `can_view`
невозможен — отклоняется `422`, и в базе стоит `CHECK (can_view OR NOT can_edit)`.

**История действий** — из `audit_log`, страницами. Индекс
`ix_audit_log_user` на `(user_id, created_at)` существует ровно под этот запрос.
Отдаются `entity`, `entity_id`, `action`, `created_at`; название раздела и
формулировку собирает клиент.

> **Отдельная работа:** у `audit_log` нет писателя. Таблица есть, эндпоинт есть,
> но записи в неё никто не делает. Нужен middleware или явные вызовы из сервисов.
> Без этого `/users/{id}/activity` вернёт пустую страницу — формально верно,
> фактически бесполезно. То же с `idempotency_key`.

### Как тестить

- `stockman` на `/users` → `403`; на `/permissions` → `403`;
- завести с занятым логином → `409`; с занятым в другом регистре → тоже `409`;
- удалить пользователя, завести нового с тем же логином → можно;
- заблокировать себя → `409`; последнего админа → `409`;
- `PUT /permissions` с `can_edit: true, can_view: false` → `422`;
- заблокировать пользователя → его access перестаёт работать **сразу**, не через
  15 минут, и цепочка refresh погашена.

### Результат

Экран «Пользователи» показывает список с фильтрами по роли, статусу и складу,
вкладка «Роли и права» — матрицу с автосохранением и откатом галочки при отказе.
Карточка сотрудника позволяет редактировать, блокировать, сменить пароль, удалить,
и показывает историю действий.

## 9. Порядок и параллельность

```
Справочник ──┐
             ├──▶ Остатки
Заказы ──────┼──▶ Отгрузка ──▶ Приёмка
             │
Пользователи ┘   (независим)
```

Разумный порядок для одного человека: **справочник → заказы → отгрузка →
приёмка → остатки → пользователи**. Справочник первым как самый простой — на нём
обкатывается рецепт из [api-architecture.md §4](api-architecture.md). Заказы
вторыми, потому что от них зависят два раздела.

На троих: справочник + остатки одному, заказы + отгрузка + приёмка второму,
пользователи третьему. Пересечений в файлах нет — раскладка по разделам это и
даёт.

Единственный шов между работами: карточка заказа показывает прогресс сборки, то
есть зовёт `/shipments/{order_id}`. Тот, кто берёт заказы, увидит пустую панель,
пока отгрузка не сделана. Это нормально и не повод менять контракт.

## 10. Что считать сделанным по разделу

1. Все операции отвечают кодами из [api.md](api.md).
2. Правила проверены тестами на голой сессии — до всякого HTTP.
3. Права: посторонняя роль получает `403`, чужой склад — `404`.
4. `check_layers.py` чист, `check_docs.py` чист.
5. **Соответствующий экран приложения заполнился живыми данными** и позволяет
   пройти сценарий целиком.

Пятый пункт — не формальность. Приложение перевели на API раньше сервера, и это
вскрыло семь несоответствий в контракте до того, как под них был написан код.
