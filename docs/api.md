# API ProЗапас — контракт

HTTP-интерфейс между десктопным приложением и сервером. 46 операций: четыре
служебных, четыре входа (раздел 4) и 38 по разделам (раздел 6).

Схема данных — [database-architecture.md](database-architecture.md), общая
картина — [architecture.md](architecture.md). Заменяет
[backend-spec_old.md](backend-spec_old.md): расхождения в разделе 10.

---

## 1. Границы

**Входит:** вход и права, справочники, остатки, заказы, отгрузка, приёмка,
пользователи, сводка для главной.

**Не входит:** оборудование (сканер, весы, принтер — служба на рабочем месте,
см. [devices-service.md](devices-service.md)), макеты этикеток (собирает
клиент), обмен с 1С.

## 2. Модель предметной области

Система обслуживает **несколько складов одной компании**. Каждый пользователь
привязан к одному складу.

Заказ — **перемещение товара между двумя складами**. Одна запись, которую две
стороны видят по-разному:

| Для склада | Условие | Что делает |
|---|---|---|
| исходящий | `to_warehouse_id` = мой | заказали мы, нам привезут — мы **принимаем** |
| входящий | `from_warehouse_id` = мой | заказали у нас — мы **отгружаем** |

Направление не хранится: у двух складов оно разное. Заказать сам у себя склад не
может — запрещено ограничением в базе.

```
        склад-отправитель                     склад-заказчик
              (входящий)                        (исходящий)
                   │                                 │
                   │            created ◀────── создал заказ
      «Принять» ──▶│  processing ──▶ резерв у отправителя
                   │
       упаковка ──▶│  коробки со штрихкодами от сервера
                   │
    «Отгрузить» ──▶│  shipped ──▶ списание у отправителя
                   │                                 │
                   │                                 │◀── сканирование коробок
                   │  received ◀──────────────── «Завершить приёмку»
                   │                            оприходование у получателя
```

Между `shipped` и `received` товара нет ни на одном складе — он в пути.

## 3. Общие правила

| | |
|---|---|
| Префикс | `/api/v1` |
| Формат | JSON, UTF-8 |
| Время | ISO 8601 в UTC |
| Количества | дробные, до трёх знаков — в справочнике есть метры и листы |
| Ошибки | RFC 9457, `application/problem+json` |

### 3.1 Склад берётся из токена

`warehouse_id` пользователя лежит в access-токене и **не передаётся в запросах**.
Сервер сам подставляет фильтр видимости:

```sql
WHERE from_warehouse_id = :мой OR to_warehouse_id = :мой
```

Клиент не может его обойти, потому что не может его задать. Заказ между складами
№1 и №3 склад №4 не увидит нигде — ни в списках, ни в счётчиках на главной.

### 3.2 Списки

```json
{"items": [...], "total": 128, "limit": 50, "offset": 0}
```

`limit` по умолчанию 50, максимум 200.

### 3.3 Ошибки

```json
{
  "type": "https://prozapas/errors/insufficient-stock",
  "title": "Недостаточно свободного остатка",
  "status": 409,
  "positions": [{"article": "100421", "requested": 500, "available": 320}]
}
```

| Код | Когда |
|---|---|
| `400` | тело или параметры не разобрались |
| `401` | нет токена, истёк, отозван |
| `403` | нет прав на раздел или запрещено правилом |
| `404` | объекта нет, удалён или принадлежит чужим складам |
| `409` | конфликт версий, недопустимый переход, нехватка остатка |
| `422` | нарушено доменное правило |
| `428` | изменение без `If-Match` |
| `503` | база недоступна |

Чужой заказ отдаёт `404`, а не `403`: существование документа чужого склада —
тоже информация.

### 3.4 Конкурентность

У `order`, `shipment`, `receipt`, `stock_balance` есть колонка `version`. Ответ
несёт `ETag`, изменение требует `If-Match`:

```
GET  /orders/60            → 200, ETag: "7"
POST /orders/60/accept     ← If-Match: "7"
                           → 409, если версия уже 8
```

Без заголовка — `428`. Это то, что не даёт двум кладовщикам отгрузить один заказ
дважды.

### 3.5 Идемпотентность

`Idempotency-Key` обязателен только на `POST /orders`: у заказа нет
естественного ключа, а повтор из-за таймаута создал бы дубль.

Коробке и приёмке ключ не нужен — их защищает уникальность штрихкода. Повторный
запрос возвращает существующий объект с `200`.

## 4. Аутентификация

```
POST /auth/login     {login, password} → {access, refresh, user, warehouse, permissions}
POST /auth/refresh   {refresh}         → {access, refresh}
POST /auth/logout    {refresh}         → 204
GET  /auth/me                          → {user, warehouse, permissions}
```

**Access** — JWT на 15 минут, на сервере не хранится:

```json
{"sub": "12", "wh": 1, "iat": 1785312000, "exp": 1785312900}
```

Внутри только идентификатор и склад. **Прав в токене нет намеренно:** админ
снимает галочку в матрице — это должно действовать на следующем запросе, а не
через пятнадцать минут. Права читаются из `role_permission` при каждой проверке.
Имени и роли там тоже нет: они меняются, а токен бы отставал, и подпись под
документом врала бы.

Склад в токене оставлен: он не меняется без перевода сотрудника, а фильтру
видимости нужен в каждом запросе.

**Refresh** — 32 случайных байта, не JWT. В базе хранится только хеш, поэтому
утечка дампа входа не даёт. Срок 30 дней, ротация при каждом обновлении: старый
отзывается. Предъявили уже отозванный — признак кражи, отзывается вся цепочка
пользователя.

Вход по полю `login` — это отдельная колонка, а не часть адреса почты.

| Ситуация | Код | `type` |
|---|---|---|
| Неверный логин или пароль | 401 | `invalid-credentials`, без уточнения |
| Пользователь заблокирован | 403 | `account-blocked` |
| Access истёк | 401 | `session-expired` — клиент обновляет и повторяет молча |
| Refresh истёк или отозван | 401 | `session-expired` — экран входа |
| Токен не разобран | 401 | `unauthorized` |

`type` даётся полным URI: `https://prozapas/errors/session-expired`. Клиент
ветвится по нему, поэтому значения стабильны — в отличие от `title`, который
переписывается вместе с формулировкой.

**Выход не требует access-токена.** Приложение простояло открытым ночь, access
истёк, человек жмёт «Выйти» — это должно сработать, а не упасть в 401.
Предъявленный refresh сам подтверждает, кто выходит, и гасится вся цепочка:
рядом мог остаться ротированный. Неизвестный токен тоже даёт 204 — иначе по
разнице в ответе видно, какой токен существует.

**`/auth/me`** возвращает ту же форму, что вход, но `access` и `refresh` в нём
`null`: у клиента они уже есть, выдавать новую пару не за что.

Пароли — argon2id. При входе проверяется `check_needs_rehash`: параметры со
временем ужесточаются, и хеш пересчитывается, пока пароль в руках. Пароль
сверяется и когда логина не существует — иначе ответ приходит заметно быстрее,
и по времени отклика перебираются учётные записи.

## 5. Права

Матрица роль × раздел, два уровня. Разделы: `orders`, `shipping`, `receiving`,
`catalog`, `stock`, `users`.

| Раздел | manager | stockman | admin |
|---|---|---|---|
| orders | просмотр + изменение | просмотр | просмотр + изменение |
| shipping | просмотр | просмотр + изменение | просмотр + изменение |
| receiving | просмотр | просмотр + изменение | просмотр + изменение |
| catalog | просмотр + изменение | просмотр | просмотр + изменение |
| stock | просмотр | просмотр + изменение | просмотр + изменение |
| users | нет доступа | нет доступа | просмотр + изменение |

Матрица читается из `role_permission` на каждой проверке, а не едет в токене.
Плата — один запрос по первичному ключу `(role_id, section)`; выигрыш — админ
снял галочку, и это действует немедленно, а не через пятнадцать минут.

Матрица приходит клиенту при входе и в `/bootstrap`, но только чтобы рисовать
интерфейс: сервер ей не верит и проверяет сам. Клиент, кстати, выбрасывает
разделы без доступа — из шести строк в памяти остаётся пять.

Блокировка действует так же сразу: она проверяется при каждом запросе, не
дожидаясь истечения access-токена, и заодно гасит всю цепочку refresh.

**Где проверяется.** Грубая проверка «раздел + уровень» — на маршруте.
Правила, которым нужен сам объект, — в сервисе: нельзя заблокировать или удалить
себя, изменить свою роль, заблокировать последнего администратора.

> Состояние на 8 августа 2026: `deps.require()` написан, но ни одним маршрутом
> ещё не вызывается — разделы, которым он нужен, не реализованы. Первым его
> получат заказы. До тех пор проверка прав не выполняется нигде, кроме входа.

## 6. Эндпоинты

### 6.1 Служебные — 4

| Метод | Путь | Права | Назначение |
|---|---|---|---|
| GET | `/health` | — | живость, делает `SELECT 1` |
| GET | `/version` | — | версия сборки и ревизия схемы |

`/bootstrap` отдаёт и список сотрудников — id, имя, склад. Он нужен фильтру
«Ответственный» на экранах заказов, отгрузки и приёмки, а `/users` для этого не
годится: тот доступен только администратору.

`/dashboard` считает по своему складу: «к отгрузке» — входящие в работе,
«к приёмке» — исходящие в пути.

### 6.2 Заказы — 7

| Метод | Путь | Права |
|---|---|---|
| GET | `/orders` | orders: view |
| POST | `/orders` | orders: edit |
| GET | `/orders/{id}` | orders: view |
| GET | `/orders/{id}/history` | orders: view |
| POST | `/orders/{id}/accept` | orders: edit |
| POST | `/orders/{id}/decline` | orders: edit |
| POST | `/orders/{id}/cancel` | orders: edit |

**`GET /orders`** — параметры: `tab` (`outgoing` / `incoming`, обязателен — это
вкладка), `status` (можно несколько), `warehouse_id` (второй склад),
`responsible_id`, `created_from`, `created_to`, `q` (префикс номера),
`limit`, `offset`.

```json
{"id": 60, "number": "2001", "status": "processing",
 "counterparty": {"id": 3, "name": "Склад №3", "owner": "ООО «Сталкер Групп»",
                  "responsible": {"id": 8, "name": "Морозова Е.В."}},
 "positions_count": 4,
 "responsible": {"id": 12, "name": "Кузнецов И.А."},
 "created_at": "…", "shipped_at": null, "accepted_at": null}
```

`counterparty` — второй склад: для исходящего это отправитель, для входящего
заказчик. Ответственный за склад приходит вместе с ним: карточка заказа
показывает ответственных обеих сторон.

**`POST /orders`** — требует `Idempotency-Key`.

```json
{"from_warehouse_id": 3, "comment": "срочно",
 "positions": [{"article": "100421", "qty": 500}]}
```

Склад-заказчик не передаётся — это наш склад из токена. Правила: отправитель
существует и не наш; позиции непустые, количества больше нуля; артикулы
существуют и не архивированы. Номер выдаёт последовательность, статус `created`,
ответственный — текущий пользователь.

**Наличие при создании не проверяется** — товар на чужом складе, отправитель сам
решит, сможет ли собрать.

**`POST /orders/{id}/accept`** — только склад-отправитель, только в `created`.
Требует `If-Match`. Переводит в `processing`, резервирует остаток, создаёт
пустую отгрузку. Не хватает свободного остатка → `409 insufficient_stock`.

**`POST /orders/{id}/decline`** — тело `{"reason": "…"}`. Только
склад-отправитель, только в `created` → `declined`.

**`POST /orders/{id}/cancel`** — тело `{"reason": "…"}`. Только склад-заказчик,
пока у отгрузки **нет ни одной коробки**. Позже → `409`. Резерв, если был,
снимается.

### 6.3 Отгрузка — 5

| Метод | Путь | Права |
|---|---|---|
| GET | `/shipments` | shipping: view |
| GET | `/shipments/{order_id}` | shipping: view |
| POST | `/shipments/{order_id}/boxes` | shipping: edit |
| DELETE | `/shipments/{order_id}/boxes/{box_id}` | shipping: edit |
| POST | `/shipments/{order_id}/ship` | shipping: edit |

Видны только заказы, где мы отправитель.

**`GET /shipments`** — параметры `status`, `q`, `weight_min`, `weight_max`,
`created_from`, `created_to`, `shipped_from`, `shipped_to`.

Вес считается как `unit_weight × qty` по позициям — индекса под этот фильтр нет,
это осознанно.

**`GET /shipments/{order_id}`** — две панели экрана:

```json
{"order": {…},
 "to_pack": [{"article": "100512", "name": "Труба стальная 32×2", "unit": "м",
              "unit_weight": 1.6,
              "ordered": 100, "packed": 37.5, "remaining": 62.5}],
 "boxes": [{"id": 7, "barcode": "WH0012001100512", "article": "100512",
            "qty": 12.5, "weight": 20.0}]}
```

**`POST …/boxes`** — тело `{"article": "100512", "qty": 12.5, "weight": 20.0}`.

Количество и вес присылаются **оба**: клиент считает количество по весу, сервер
сверяет их между собой и с остатком по позиции. Если считать только на сервере,
ошибка весов молча станет ошибкой количества.

Ответ — созданная коробка со штрихкодом от сервера (см. 8.1). Упаковано больше
заказанного → `422`.

Ограничения на вес коробки нет: одну позицию можно паковать в сколько угодно
коробок.

**`DELETE …/boxes/{box_id}`** → `204`. Этикетка не вышла или коробку
переупаковали.

**`POST …/ship`** — требует `If-Match`. Частичная отгрузка разрешена: ответ
содержит недостачу по позициям, чтобы клиент показал подтверждение. Нет ни одной
коробки → `409`.

### 6.4 Приёмка — 5

| Метод | Путь | Права |
|---|---|---|
| GET | `/receipts` | receiving: view |
| GET | `/receipts/{order_id}` | receiving: view |
| POST | `/receipts/{order_id}/boxes/{barcode}/receive` | receiving: edit |
| DELETE | `/receipts/{order_id}/boxes/{barcode}/receive` | receiving: edit |
| POST | `/receipts/{order_id}/complete` | receiving: edit |

Видны только заказы, где мы получатель и статус `shipped`.

**`GET /receipts/{order_id}`** отдаёт **настоящие коробки отправителя** — те
самые, что он упаковал. Ничего не синтезируется:

```json
{"order": {…},
 "boxes": [{"barcode": "WH0012001100512", "article": "100512",
            "name": "Труба стальная 32×2", "qty": 12.5,
            "weight": 20.0, "received_at": null, "actual_weight": null},
           {"barcode": "WH0012001100512-02", "…": "…",
            "received_at": "…", "actual_weight": 19.8,
            "diff_kg": -0.2, "diff_percent": -1.0}]}
```

Расхождение считается сервером из `weight` и `actual_weight`, не хранится.

**`POST …/boxes/{barcode}/receive`** — тело `{"actual_weight": 19.8}`.

Ключ пути — штрихкод, а не внутренний id: сканер даёт именно его. Идемпотентен —
коробка уже принята, возвращаем как есть.

**`DELETE …/boxes/{barcode}/receive`** → `204`. Отмена ошибочного скана.

**`POST …/complete`** — требует `If-Match`. Приходует **принятые** коробки,
закрывает документы. Коробки без отметки — зафиксированная недостача, заказ всё
равно переходит в `received`. Отдельного «отметить недостачу» нет.

### 6.5 Остатки — 5

| Метод | Путь | Права |
|---|---|---|
| GET | `/stock` | stock: view |
| GET | `/stock/summary` | stock: view |
| GET | `/stock/{item_id}` | stock: view |
| GET | `/stock/{item_id}/movements` | stock: view |
| POST | `/stock/operations` | stock: edit |

**`GET /stock`** — `q`, `warehouse_id`, `below_min`, `in_stock`, `limit`, `offset`.
Элемент: артикул, код 1С, наименование, единица, `qty`, `free` (= `qty − reserved`),
`reserved`, плюс `by_warehouse` — разбивка по складам.

`in_stock` по умолчанию `true`: экран «Остатки» показывает то, что лежит на
складе, а не всю номенклатуру. Вместе с `below_min=true` его надо снимать —
позиция, которой ноль при минимуме пятьдесят, как раз и требует дозаказа.

Разбивка нужна экрану «Новый заказ» в режиме «найти где есть»: он предлагает
склад с наибольшим остатком, а остальные раскрывает дочерними строками. Как
только склад выбран, режим выключается и достаточно `warehouse_id`. Название
склада в разбивке не дублируется — клиент берёт его из `/bootstrap`.

**`GET /stock/summary`** — четыре карточки экрана: всего позиций, ниже минимума,
в резерве, свободный остаток.

**`POST /stock/operations`** — ручная операция из карточки товара:

```json
{"article": "100512", "warehouse_id": 1, "type": "writeoff",
 "qty": 12.5, "comment": "брак при разгрузке"}
```

Типы: `receipt`, `shipment`, `writeoff`, `recount`. Для `recount` `qty` — не
дельта, а новое значение. У списания и корректировки документа нет: `doc_type`
и `doc_id` пустые, в истории показывается `comment`.

запрос. Элемент: `entity`, `entity_id`, `action`, `created_at`. Название раздела
и формулировку действия собирает клиент — он и так переводит статусы заказа,
а на сервере это была бы вторая копия тех же строк.

## 7. Три транзакции

Вся бизнес-логика сходится в трёх местах. Каждая — одна транзакция целиком.

### 7.1 Принять заказ

```
проверки:  version совпал · статус created · мы отправитель
           свободный остаток >= заказанного по каждой позиции
───────────────────────────────────────────────────────────
reserved += qty по каждой позиции
движение reserve
order.status = processing
событие статуса
создаётся пустая отгрузка
```

### 7.2 Отгрузить

```
проверки:  version совпал · есть хотя бы одна коробка · мы отправитель
───────────────────────────────────────────────────────────
qty      -= упаковано
reserved -= заказано          ← весь резерв, не только упакованное
движение shipment на упакованное
shipment.status = done, shipped_at
order.status = shipped, shipped_at
событие статуса
```

Резерв снимается полностью: второй отгрузки по заказу не будет, разница
возвращается в свободный остаток.

### 7.3 Завершить приёмку

```
проверки:  version совпал · статус приёмки progress · мы получатель
───────────────────────────────────────────────────────────
qty += сумма по принятым коробкам   ← принятым, не отгруженным
движение receipt
receipt.status = done, accepted_at
order.status = received, accepted_at
событие статуса
```

Непринятые коробки остаются без `received_at` — это и есть недостача.

## 8. Правила

### 8.1 Штрихкод коробки

Выдаёт сервер при создании коробки:

```
WH{id склада-заказчика}{номер заказа}{артикул}        первая коробка
WH{id склада-заказчика}{номер заказа}{артикул}-02     вторая
WH{id склада-заказчика}{номер заказа}{артикул}-03     третья
```

`NN` считается **внутри артикула**, а не по всем коробкам отгрузки. Первая
коробка суффикса не получает никогда, поэтому переименовывать уже наклеенную
этикетку не приходится.

Id склада дополняется до трёх знаков: без этого «склад 1, заказ 22001» и
«склад 12, заказ 2001» дают одну строку.

### 8.2 Отметки о печати нет

Этикетка печатается сразу после создания коробки, через локальную службу
устройств, минуя API. Не вышла — клиент удаляет коробку. Значит существующая
коробка всегда напечатана, а перепечать доступна в любой момент и ничего не
меняет в данных.

### 8.3 Статусы заказа

```
created ──▶ processing ──▶ shipped ──▶ received
   │             │
   ▼             ▼
declined     cancelled
```

`accept` и `decline` — только отправитель в `created`. `cancel` — только
заказчик, пока нет коробок. Остальное → `409 invalid_transition`.

### 8.4 Что не хранится

| | Откуда берётся |
|---|---|
| Направление заказа | сравнение складов с моим |
| Расхождение веса | `actual_weight − weight` |
| Прогресс сборки и приёмки | подсчёт коробок |
| Недостача | коробки без `received_at` |
| Свободный остаток | `qty − reserved` |
| Вес заказа | `unit_weight × qty` по позициям |

## 9. Число запросов

Отгрузка и приёмка симметричны:

```
GET  список
GET  карточка
POST операция × число коробок
POST завершение
──
3 + N запросов
```

Запрос на коробку сохранён осознанно: кладовщик видит результат сразу, каждая
операция независима и идемпотентна, прогресс виден другим в реальном времени.
Локального накопления и очереди отправки нет.

Реализовано 8 операций из 46: служебные четыре и вход целиком. Клиент покрывает
контракт полностью — все 46 методов есть в `desktop/app/api/resources.py`, и
экраны разделов упираются в `404`, пока сервер их не отдаёт.

- [x] OpenAPI генерируется из кода. Сверено с [openapi.json](openapi.json) по
      реализованным операциям: лишнего нет, пути и методы совпадают.
- [x] Вход, обновление, выход; отозванный refresh обрушивает цепочку.
- [ ] Склад №4 не видит заказ между №1 и №3 ни одним эндпоинтом.
      `services/visibility.py` написан, но заказов ещё нет — проверять нечем.
- [ ] Права применяются: `stockman` не открывает `/users`. `deps.require()`
      написан, ни одним маршрутом пока не вызывается.

- [ ] Отгрузка и приёмка атомарны: сбой не оставляет ни движения, ни статуса.

- [ ] Заказ в метрах проходит путь без округления.
