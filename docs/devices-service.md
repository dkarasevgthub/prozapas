# Служба устройств ProЗапас — техническое задание

Отдельная программа, которая держит складское оборудование и отдаёт его
приложению ProЗапас через именованный канал.

Приложение не открывает ни одного порта и ничего не знает о моделях устройств:
оно шлёт команды вида `{"cmd": "print"}` и принимает события вида
`{"event": "scan"}`. Всё, что касается железа, живёт только здесь.

---

## 1. Границы работы

**Входит:** драйверы сканера, весов и принтера этикеток; сервер именованного
канала; очередь печати; конфигурация; логирование; отладочная консоль; сборка в
исполняемый файл.

**Не входит:** интерфейс (его нет вообще), бизнес-логика склада, работа с
данными приложения, макеты этикеток (служба печатает переданные ей байты, ZPL
формирует приложение).

## 2. Стек

| | |
|---|---|
| Python | 3.13 |
| Цикл событий | `QCoreApplication` из PyQt6 — без виджетов, окна нет |
| COM-порты | `QtSerialPort` (входит в PyQt6, ставить нечего) |
| Печать | `pywin32` → `win32print` |
| Сервер канала | `QLocalServer` из `PyQt6.QtNetwork` |
| Сборка | PyInstaller, один файл `devices.exe` |

`QCoreApplication` выбран намеренно: он даёт тот же асинхронный цикл событий,
что и в приложении, поэтому `QSerialPort` и `QLocalServer` работают без потоков.
Потоки нужны только для печати — вызовы спулера блокирующие.

## 3. Структура

```
devices/
    __main__.py          точка входа, разбор аргументов, цикл событий
    server.py            QLocalServer: клиенты, разбор строк, ответы, рассылка
    session.py           одно подключение: версия протокола, подписки
    config.py            чтение и запись devices.toml
    logging_setup.py     файл с ротацией
    cli.py               отладочная консоль (вброс событий)
    drivers/
        base.py          общий интерфейс драйвера: состояние, open/close, сигналы
        scanner.py       COM-порт → сигнал scanned(code)
        scale.py         COM-порт → поток показаний, чтение устойчивого веса
        printer.py       win32print + очередь заданий
        fake.py          подставные драйверы для тестов и разработки
    protocol.py          ОБЩИЙ с приложением модуль: имена команд, событий, ошибок
```

`protocol.py` — единственный файл, который используют обе стороны. Он должен
собираться и в `devices.exe`, и в приложение; расхождение имён недопустимо.

## 4. Протокол

### 4.1 Кадрирование

Именованный канал `prozapas-devices` (на Windows это `\\.\pipe\prozapas-devices`).
По каналу идут строки: один JSON-объект в строке, UTF-8, разделитель `\n`.

Три вида сообщений:

```
запрос   {"id": 17, "cmd": "print", ...}     от приложения, всегда с id
ответ    {"id": 17, "ok": true, ...}         от службы, тот же id
событие  {"event": "scan", ...}              от службы по своей инициативе, без id
```

`id` — целое, счётчик в пределах соединения. Отвечать разрешено не по порядку.
Неизвестную команду **нельзя игнорировать** — на неё отвечают ошибкой
`unknown_command`, иначе после независимого обновления сторона зависнет в
ожидании.

### 4.2 Команды

| Команда | Параметры | Ответ |
|---|---|---|
| `hello` | `protocol` (int), `client` (str) | `service` (str), `protocol` (список поддерживаемых версий) |
| `devices` | — | `devices`: `{"scanner": "online", "printer": "offline", "scale": "online"}` |
| `subscribe` | `events`: `["weight"]` | — |
| `unsubscribe` | `events`: `["weight"]` | — |
| `print` | `key`, `format` (`zpl`/`tspl`/`raw`), `payload` (str), `copies` (int) | `job` (str), `state` |
| `print.status` | `job` | `state` |
| `print.queue` | — | `jobs`: `[{"job", "state"}]` |
| `print.retry` | `job` | `state` |
| `scale.read` | `stable` (bool), `timeout_ms` (int) | `value` (float), `unit`, `stable` |
| `scale.tare` | — | — |
| `shutdown` | — | — |

Пример:

```json
→ {"id": 43, "cmd": "print", "key": "box-SH3029201204-01", "format": "zpl",
   "payload": "^XA^FO40,40^A0N,30,30^FDSH3029201204-01^FS^XZ", "copies": 1}
← {"id": 43, "ok": true, "job": "j-104", "state": "queued"}
```

`key` — ключ идемпотентности. Повторный `print` с тем же ключом **не создаёт
второе задание**, а возвращает прежнее с его текущим состоянием. Приложение
пользуется этим при обрыве связи.

### 4.3 События

| Событие | Поля | Когда |
|---|---|---|
| `scan` | `code`, `device` | сканер прислал штрихкод |
| `weight` | `value`, `unit`, `stable` | пока есть подписка |
| `device` | `id`, `state`, `reason` | устройство подключили, отключили, ошибка |
| `job` | `job`, `state`, `error` | задание печати сменило состояние |

Состояния устройства: `online`, `offline`, `error`.
Состояния задания: `queued`, `printing`, `done`, `failed`.

### 4.4 Ошибки

```json
{"id": 18, "ok": false, "error": {"code": "printer_offline", "message": "Принтер не отвечает"}}
```

Коды: `bad_request`, `unknown_command`, `no_device`, `printer_offline`,
`scale_timeout`, `busy`, `internal`. Приложение принимает решения по коду, текст
показывается пользователю.

### 4.5 Версия

`hello` — первое сообщение после подключения. Служба возвращает список версий,
которые понимает. Если версии клиента нет в списке, приложение показывает
«служба устройств несовместима» и переходит в ручной режим. Текущая версия — 1.

## 5. Требования к драйверам

### 5.1 Общее

Каждый драйвер:

- открывает своё устройство при старте службы и держит его всё время работы;
- имеет состояние `online` / `offline` / `error` и сообщает об изменениях;
- при потере устройства (`ResourceError` у порта, исчезнувший принтер) переходит
  в `offline` и пробует переоткрыть раз в 5 секунд;
- никогда не роняет службу: любое исключение драйвера логируется и переводит
  устройство в `error`.

Устройство, не заданное в конфигурации, находится в состоянии `offline` — это не
ошибка.

### 5.2 Сканер

Подключение — USB в режиме виртуального COM-порта (переключается служебным
штрихкодом из инструкции сканера). Читаем поток, накапливаем до `\r` или `\n`,
отдаём строку событием `scan`.

Требования:

- **дедупликация**: тот же код в пределах 500 мс не отправляется повторно
  (сканеры дублируют при удержании);
- обрезка пробелов и служебных символов, приведение к верхнему регистру;
- пустая строка игнорируется.

Режим HID (эмуляция клавиатуры) в задачу **не входит**: если сканер окажется
только HID, это отдельная работа на стороне приложения.

### 5.3 Весы

Подключение — USB в режиме виртуального COM-порта. Протокол зависит от модели
(уточняется, см. раздел 12), поэтому разбор строки выносится в отдельную функцию
с тестами на реальных примерах ответа.

Два режима работы, оба должны поддерживаться:

- **поток** — весы шлют показания сами, драйвер их только разбирает;
- **опрос** — весы отвечают на запрос, драйвер опрашивает 5 раз в секунду.

Наружу разницы быть не должно: в обоих случаях события `weight` идут одинаково.

Требования:

- **устойчивость**: показание считается устойчивым, если три подряд отличаются
  меньше чем на шаг весов (по умолчанию 10 г), либо если сами весы сообщают
  признак стабильности в своём протоколе — тогда доверять ему;
- **ограничение частоты**: события `weight` не чаще 10 раз в секунду и только
  когда значение изменилось больше чем на шаг либо переключился признак
  устойчивости;
- события шлются **только подписчикам** (`subscribe weight`); без подписки
  драйвер продолжает читать порт, но в канал ничего не отправляет;
- `scale.read` с `stable: true` ждёт устойчивое показание до `timeout_ms`, по
  истечении отвечает ошибкой `scale_timeout` — приложение в этом случае покажет
  окно ручного ввода веса.

### 5.4 Принтер

Подключение — USB, принтер зарегистрирован в системе. Печать заданием типа
`RAW` через `win32print`: команды передаются принтеру как есть, без обработки
драйвером.

Отправка блокирующая — выполняется в отдельном потоке, цикл событий блокировать
нельзя.

Очередь заданий:

- задание принимается **всегда**, даже если принтер офлайн, и встаёт в очередь
  со статусом `queued`;
- при ошибке — три повтора с паузами 2, 5, 10 секунд, после чего `failed`;
  задание остаётся в очереди и повторяется командой `print.retry`;
- очередь переживает переподключение приложения, но **не** перезапуск службы
  (сохранять на диск не требуется);
- на каждое изменение состояния — событие `job`.

## 6. Конфигурация

Файл `%ProgramData%\ProZapas\devices.toml`, создаётся при первом запуске со
значениями по умолчанию.

```toml
[pipe]
name = "prozapas-devices"
idle_timeout_sec = 30        # 0 — не завершаться без клиентов

[scanner]
port = "COM3"                # пусто — устройство отключено
baud = 9600

[scale]
port = "COM4"
baud = 9600
model = "masa-k"             # какой разбор протокола применять
step_g = 10                  # шаг весов для оценки устойчивости

[printer]
name = "ZDesigner ZD230-203dpi ZPL"
encoding = "cp866"

[log]
level = "info"
path = ""                    # пусто — %ProgramData%\ProZapas\devices.log
```

Служба должна уметь перечислять доступные порты и принтеры — это нужно
приложению для экрана настроек оборудования:

```
devices.exe --list-ports        COM3  Honeywell Scanner  VID:0C2E PID:0B61
devices.exe --list-printers     ZDesigner ZD230-203dpi ZPL  (по умолчанию)
```

## 7. Жизненный цикл

Запускается дочерним процессом приложения; регистрация службой Windows —
опциональный режим развёртывания, поведение программы от этого не меняется.

```
старт
 ├─ прочитать конфигурацию, поднять лог
 ├─ открыть устройства (недоступные — просто offline)
 ├─ listen("prozapas-devices")
 │    занят → в лог «уже запущен», выход с кодом 2
 ├─ напечатать в stderr строку `ready` (по ней приложение понимает, что можно подключаться)
 └─ цикл событий

работа
 ├─ клиентов может быть несколько; события рассылаются всем подписчикам
 └─ нет ни одного клиента дольше idle_timeout_sec → корректный выход
      (страховка от «сирот», если приложение упало)

остановка
 ├─ команда shutdown либо сигнал завершения
 ├─ дописать текущее задание печати, очередь не терять молча — записать в лог
 └─ закрыть порты, выйти с кодом 0
```

Коды возврата: `0` — штатно, `2` — канал занят, `3` — конфигурация повреждена.

## 8. Логирование

Файл с ротацией (5 файлов по 2 МБ). В `info` — старт, состояния устройств,
принятые и напечатанные задания. В `debug` — каждое сообщение канала целиком:
при разборе жалоб со склада это первое, что смотрят.

Штрихкоды и веса логировать можно, ничего чувствительного в них нет.

## 9. Отладочная консоль

Отдельная точка входа, подключается к каналу как обычный клиент и вбрасывает
события. Нужна для проверки сценариев, которые иначе воспроизводятся только
выдёргиванием проводов, и для показа системы без железа.

```
python -m devices.cli scan WH1281187100421
python -m devices.cli weight 22.4 --stable
python -m devices.cli device printer offline --reason unplugged
python -m devices.cli print-queue
```

## 10. Тестирование

Обязательное покрытие:

**Протокол** — кодирование и разбор, сопоставление ответа с запросом,
неизвестная команда, битая строка, несовпадение версии.

**Сервер** — несколько клиентов одновременно; подписка и отписка на `weight`;
рассылка событий только подписчикам; корректный выход по `idle_timeout_sec`.

**Драйверы COM** — против виртуальной пары портов (`com0com`): тест пишет в один
конец реальные байты протокола, драйвер читает из другого. Проверяется разбор
формата, склейка пакета из двух чтений, мусор в порту, обрыв на середине строки,
дедупликация сканов, определение устойчивости веса.

**Принтер** — подставной принтер, пишущий задание в файл. Проверяется: печать
при недоступном принтере ставит задание в очередь; повтор с тем же `key` не
создаёт второе задание; после трёх неудач состояние `failed`; `print.retry`
возвращает задание в очередь.

**Сквозной сценарий** — служба с подставными драйверами запускается
подпроцессом, приложение поднимается offscreen, проигрывается приёмка коробки:
скан → взвешивание → печать → завершение.

Сценарии отказов, которые должны быть в тестах явно:

- службы нет при старте приложения;
- служба перезапустилась во время работы;
- принтер выдернули между созданием коробки и печатью;
- весы молчат дольше таймаута;
- один и тот же скан пришёл дважды за 200 мс.

## 11. Сборка и поставка

PyInstaller, один файл `devices.exe`, кладётся рядом с исполняемым файлом
приложения. Версия — в `--version` и в ответе на `hello`.

Обновление: остановить приложение (служба завершится сама по холостому
таймауту), заменить exe, запустить приложение. Протокол при этом может остаться
прежним — тогда версии сторон разъезжаться не будут.

## 12. Что нужно уточнить до начала

1. **Модели устройств** — сканера, весов и принтера. От них зависят: протокол
   разбора показаний весов, набор команд принтера (ZPL или TSPL) и то, поддержит
   ли сканер режим COM-порта.
2. **Кодировка принтера** — `cp866` или `cp1251`, зависит от прошивки.
3. **Шаг весов** и наличие признака стабильности в их протоколе.

Пока этого нет, всё остальное — сервер, протокол, очередь печати, конфигурация,
тесты — пишется и проверяется на подставных драйверах.

## 13. Критерии приёмки

- [ ] Приложение подключается к каналу, `hello` проходит, состояния устройств
      отображаются в блоке «Оборудование» в меню.
- [ ] Скан коробки на экране приёмки работает от сканера, без ввода с клавиатуры.
- [ ] Вес на панели «ВЕСЫ» меняется в реальном времени, устойчивое показание
      фиксируется.
- [ ] Этикетка печатается по нажатию, перепечать не создаёт вторую коробку.
- [ ] Выдёргивание любого устройства меняет статус в меню за секунды и не роняет
      ни приложение, ни службу; после обратного подключения всё восстанавливается.
- [ ] При остановленной службе приложение работает в ручном режиме: штрихкод
      вводится с клавиатуры, вес в модальном окне, отгрузка заблокирована.
- [ ] Тесты из раздела 10 проходят без подключённого оборудования.
