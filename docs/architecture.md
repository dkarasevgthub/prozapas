# ProЗапас — архитектура: принятые решения и обоснования

Выжимка проектного обсуждения от 27 июля 2026. Документ описывает, к чему
пришли, какие были варианты и почему выбран именно этот. Там, где решение может
поменяться, указано условие, при котором к нему стоит вернуться.

Детальное ТЗ на службу устройств вынесено отдельно — [devices-service.md](devices-service.md).

---

## 1. Где сейчас данные

> **Раздел исторический.** Описанного здесь файла больше нет: все экраны ходят
> в API через [desktop/app/api](../desktop/app/api), контракт — [api.md](api.md).
> Оставлено, чтобы решения ниже читались вместе с тем, от чего уходили.

Всё хранилось в одном файле `desktop/mock_data.json`. Ничего не дублировалось:
позиция заказа, строка остатков и коробка хранили только артикул, а наименование,
единица и вес брались из справочника.

```
version           номер схемы, по нему шла миграция
reference         warehouseCode, warehouses, roles, sections, catalog
stock             [{article, byWarehouse:{склад: кол-во}, reserved, minQty}]
orders            [{id, number, direction, status, positions:[{article, qty}], history}]
users             [{id, fullName, role, warehouse, …}]
permissions       {роль: {раздел: {view, edit}}}
receiving         batches[] + progress{} — партии и прогресс сканирования
shipping          packing{} — коробки, веса, кто упаковал
session           {currentUserId}
```

Что осознанно **не** делалось: остатки не пересчитывались при движении товара.
Отгрузка и приёмка меняли статусы заказов, но не списывали и не приходовали
количество. Это бизнес-логика, её место — на сервере, и там она теперь и описана:
три транзакции в [api.md §7](api.md).

Две вещи из этой схемы не выжили. `direction` у заказа: у двух складов он разный,
поэтому направление вычисляется, а не хранится. Партии приёмки от поставщиков:
приёмка всегда принимает отгрузку другого склада. Разбор — в [api.md §10](api.md).

## 2. Переход на серверную архитектуру

### 2.1 Общая схема

```
Десктоп (PyQt6)  ──HTTPS/JSON──▶  API (FastAPI)  ──▶  PostgreSQL
   репозитории                     RBAC, транзакции      миграции Alembic
   кэш справочников                OpenAPI-контракт
```

Стек: **FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic v2 + PostgreSQL**, uvicorn
за nginx, всё в Docker Compose. Причина выбора не в популярности: FastAPI сам
генерирует OpenAPI, а из него — типизированный клиент для десктопа, поэтому
контракт не расходится с кодом.

### 2.2 Сущности — 15 таблиц

| Таблица | Ключевые поля |
|---|---|
| `warehouse` | id, code, name, responsible_user_id |
| `user_account` | id, full_name, email, password_hash, role_id, warehouse_id, position, status |
| `role` | id, code, label |
| `role_permission` | role_id, section, can_view, can_edit |
| `catalog_item` | id, article (uniq), code1c, name, unit, unit_weight, is_archived |
| `stock_balance` | item_id, warehouse_id, qty, reserved, min_qty, **version** |
| `stock_movement` | id, item_id, warehouse_id, delta, type, doc_ref, comment, user_id, created_at |
| `order` | id, number (uniq), direction, status, counterparty_warehouse_id, responsible_user_id, **version** |
| `order_position` | id, order_id, item_id, qty |
| `order_status_event` | id, order_id, status, user_id, reason, occurred_at |
| `shipment` | id, order_id (uniq), status, responsible_user_id, shipped_at |
| `shipment_box` | id, shipment_id, barcode (uniq), item_id, qty, weight, printed_at |
| `supplier` | id, name, inn |
| `receipt_batch` | id, number, supplier_id, order_id, ship_at, created_at, status, accepted_at |
| `receipt_batch_position` | id, batch_id, item_id, boxes, box_weight |
| `receipt_scan` | id, batch_id, barcode, item_id, expected_weight, actual_weight, is_missing |

Плюс инфраструктурные: `refresh_token`, `audit_log`, `idempotency_key`.

### 2.3 Три решения по модели данных

**Числовые id вместо имён.** Сейчас склад — строка «Склад №1», она же ключ
остатков и поле заказа; переименование склада ломает данные. На сервере —
`warehouse_id`, имя только для показа.

**Остаток = журнал + баланс.** `stock_movement` — append-only, `stock_balance` —
текущее значение под оптимистичной блокировкой. Баланс всегда можно пересчитать
и сверить с журналом.

**Текущий склад в сессии.** Приложение работает от лица одного склада (в коде
это `warehouseCode = "128"`), «входящие/исходящие» считаются относительно него.
На сервере это поле пользователя, а не константа.

### 2.4 Эндпоинты — около 50, префикс `/api/v1`

```
auth        4    login · refresh · logout · me
справочники 9    bootstrap · warehouses · catalog · roles · permissions
остатки     5    список · summary · по складам · движения · ручная операция
заказы      7    список · создание · карточка · accept/decline/cancel · история
отгрузка    7    список · карточка · коробки · печать · отгрузить · этикетка
приёмка     5    список · карточка · сканы · отмена скана · завершить
пользователи 8   CRUD · блокировка · смена пароля
служебное   3    dashboard · health · version
```

### 2.5 Правила «продового» API

- **Версия в пути** `/api/v1`; списки всегда `{items, total, limit, offset}`.
- **Ошибки** — RFC 9457 `application/problem+json` с машиночитаемым `type`.
- **Конкурентность** — у `order`, `shipment`, `stock_balance` колонка `version`,
  наружу `ETag`, изменение требует `If-Match`, конфликт → `409`. Без этого два
  кладовщика отгрузят один заказ дважды.
- **Идемпотентность** — `Idempotency-Key` на создание заказа, коробки и скана.
- **Транзакции** — списание остатка, движение и смена статуса коммитятся вместе.
- **Миграции** Alembic с первого дня, сид — отдельным скриптом.
- **Наблюдаемость** — structlog с request-id, `/health`, метрики, Sentry,
  `audit_log` на действия с документами.

## 3. Сервисная архитектура

### 3.1 Модульный монолит, а не микросервисы

Для склада одной компании выбран **модульный монолит с сервисным слоем**: один
процесс, одна база, но границы между доменами проведены строго, как если бы это
были отдельные сервисы.

Главный аргумент — транзакции. «Принять заказ и зарезервировать остаток» в
монолите одна транзакция; в микросервисах это сага с компенсациями.

### 3.2 Восемь доменных сервисов

```
             ┌─ orders ─┐   ┌─ shipping ─┐   ┌─ receiving ─┐
             └────┬─────┘   └─────┬──────┘   └──────┬──────┘
                  └───────────────┼─────────────────┘
                          ┌───────▼────────┐
                          │   inventory    │
                          └───────┬────────┘
                          ┌───────▼────────┐
                          │    catalog     │
                          └────────────────┘
        accounts · labeling · dashboard — сбоку, зависимости не циклятся
```

| Сервис | Отвечает за |
|---|---|
| `accounts` | вход, токены, пользователи, роли, права |
| `catalog` | номенклатура, склады, поставщики |
| `inventory` | остатки, резервы, журнал движений, точка дозаказа |
| `orders` | жизненный цикл заказа и статусы |
| `shipping` | сборка, коробки, взвешивание, факт отгрузки |
| `receiving` | партии, сканирование, расхождения, факт приёмки |
| `labeling` | выдача штрихкодов, шаблоны и рендер этикеток, журнал печати |
| `dashboard` | сводка для главной, только чтение |

Сквозные: `audit`, `notifications`, `integration` (обмен с 1С).

### 3.3 Правила, которые делают границы настоящими

- **Сервис читает только свои таблицы.** Нужны чужие данные — вызов метода
  чужого сервиса, а не `JOIN` через границу. Как только `shipping` сделает
  джойн на `stock_balance`, граница исчезла.
- **Зависимости направлены вниз.** `catalog` и `inventory` никого не зовут;
  наверх информация идёт событиями (`order.shipped`, `stock.below_min`).
- **Транзакция принадлежит вызывающему** и передаётся вниз.

Структура каждого сервиса одинаковая: `api.py` (только HTTP) → `service.py`
(правила и транзакции) → `repository.py` (свои таблицы) → `models.py`.

### 3.4 Что выносить первым, если дойдёт до разделения

`labeling` и устройства, `integration` с 1С, `notifications`. А `orders` и
`inventory` разделять не стоит никогда: у них общий инвариант «нельзя отгрузить
больше, чем есть».

Триггеры перехода к микросервисам: несколько складов с независимыми командами,
раздельные релизы частей, нагрузка на что-то одно.

## 4. Где разместить сервер

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Мини-ПК на складе** | работает при обрыве интернета; данные не выходят за периметр; 1С рядом | бэкапы и питание — свои; снаружи через VPN |
| VPS у хостера | доступен отовсюду, бэкапы провайдера, ~500–1000 ₽/мес | нет интернета — встала работа |
| Гибрид | сервер на складе, ночной бэкап в облако | чуть больше настройки |

**Выбран сервер на месте.** Приёмка и отгрузка — работа руками у стеллажа, она
не должна останавливаться из-за провайдера.

Железо: 2 ядра, 4 ГБ памяти, 40 ГБ диска с запасом на годы. Три контейнера
(`api`, `db`, `nginx`), тот же compose-файл для разработки. TLS — внутреннее имя
и сертификат внутреннего CA; наружу выставлять только через VPN. Бэкап —
`pg_dump` по расписанию плюс копия на другой носитель.

## 5. Оборудование

### 5.1 USB — это только провод

Программно важно, каким классом устройство представляется системе:

| Класс | Что видит Windows | Через что работаем |
|---|---|---|
| USB CDC (виртуальный COM) | порт `COM3` | `QtSerialPort` — уже установлен |
| USB HID keyboard | вторую клавиатуру | перехват событий или Raw Input API |
| USB Printer class | принтер в списке | `win32print`, задание типа `RAW` |
| USB HID POS scale | HID с профилем весов | `hidapi` |
| Vendor-specific | «неизвестное устройство» | `pyusb` + подмена драйвера — не использовать |

### 5.2 Выбранный режим для каждого устройства

- **Сканер — USB-COM.** Переключается служебным штрихкодом из инструкции. Фокус
  не важен, скан не спутать с клавиатурой, и нет проблемы русской раскладки
  (в HID-режиме `WH128` приезжает как `ЦР128`).
- **Принтер — RAW через спулер.** Команды ZPL/TSPL передаются как есть; драйвер
  ничего не рендерит. Если у принтера есть Ethernet, предпочтительнее сокет на
  порт 9100 — тогда не нужен даже `pywin32`.
- **Весы — USB-COM**, протокол по модели.

### 5.3 Ключевые правила работы с железом

- **Коробка создаётся до печати, а не после.** Зажевало ленту — коробка на
  месте, этикетка перепечатывается. Обратный порядок теряет данные.
- **Перепечать не создаёт вторую коробку** — в журнале печати флаг `is_reprint`.
- **Штрихкод выдаёт сервер**, а не клиент: при двух рабочих местах коробки
  получат одинаковые коды.
- **Отказ устройства не блокирует работу.** Нет сканера — ручной ввод; нет
  весов — модальное окно; нет принтера — единственное исключение, отгрузка
  блокируется, потому что коробка без этикетки бессмысленна.
- **Шаблон этикетки хранится на сервере.** Смена макета — правка в базе, а не
  новая сборка приложения на всех рабочих местах.

## 6. Служба устройств

### 6.1 Рассмотренные варианты

| Вариант | Итог |
|---|---|
| Драйверы внутри приложения | Отклонён: интерфейсный процесс держит порты, зависший драйвер роняет приложение |
| Агент на HTTP `127.0.0.1` | Отложен: порт доступен любой программе и любой странице в браузере, нужен токен и защита от чужих запросов; агент уходит на asyncio, драйверы перестают быть общим кодом |
| **Именованный канал** | **Выбран** |

### 6.2 Почему канал

- **Безопасность.** Канал ограничен списком доступа Windows и по сети
  недостижим физически. У локального HTTP-порта поверхность атаки есть всегда.
- **Общий код драйверов.** Канал живёт в том же цикле событий Qt, что и
  приложение, поэтому драйверы пишутся один раз.
- **Ноль зависимостей.** `QLocalServer`/`QLocalSocket` входят в PyQt6.

Реальное время для весов, независимый перезапуск и обновление отдельным файлом
одинаково работают в обоих вариантах — по этим пунктам разницы нет.

**Условие пересмотра:** появляется третья сторона, которой нужны те же
устройства — веб-клиент, 1С, или устройства на отдельной коробке, к которой
ходят с нескольких машин. Тогда HTTP из недостатка становится преимуществом.

### 6.3 Разделение ответственности

```
ProЗапас                                   devices
├── devices/gateway.py    клиент канала    ├── drivers/scanner.py    COM-порт
├── devices/protocol.py   ─── общий ──────▶├── drivers/scale.py      COM-порт
└── devices/fake.py       симуляция        ├── drivers/printer.py    спулер
                                            └── server.py            канал
```

В приложении нет ни одной строчки про железо: ни `pyserial`, ни `win32print`, ни
имён портов. Оно знает только `{"cmd": "print"}` и `{"event": "scan"}`.

### 6.4 Запуск

Дочерний процесс приложения: стартует с ProЗапас, гасится при выходе, установка
и права администратора не нужны. Тот же `devices.exe` можно зарегистрировать
службой Windows — это настройка развёртывания, программа не меняется.

Страховка от процессов-сирот: служба сама завершается, если ни один клиент не
подключён дольше 30 секунд.

### 6.5 Протокол

Именованный канал `prozapas-devices`, по строке JSON на сообщение, UTF-8.

```
запрос   {"id": 17, "cmd": "print", ...}
ответ    {"id": 17, "ok": true, ...}
событие  {"event": "scan", ...}
```

Команды: `hello`, `devices`, `subscribe`, `unsubscribe`, `print`,
`print.status`, `print.queue`, `print.retry`, `scale.read`, `scale.tare`,
`shutdown`.

События: `scan`, `weight`, `device`, `job`.

Полное описание с параметрами, кодами ошибок и требованиями к драйверам — в
[devices-service.md](devices-service.md).

### 6.6 Вес в реальном времени

Весы шлют 10–50 показаний в секунду; агент фильтрует (изменение больше шага
весов либо переключение признака устойчивости) и отдаёт не чаще 10 раз в
секунду. Задержка от весов до цифры на экране — меньше 50 мс.

Две вещи, которые надо заложить сразу:

- событие `weight` меняет **текст одного ярлыка**, а не вызывает пересборку
  страницы — иначе интерфейс превратится в мигающее слайд-шоу;
- подписка на вес включается на экране, где он нужен, и выключается при уходе.

Это открывает автофиксацию: вес устойчив дольше секунды — приложение само
подставляет его в расчёт количества, нажимать ничего не нужно.

## 7. Тестирование оборудования без оборудования

| Что | Чем |
|---|---|
| Протокол | обычный pytest, чистые функции |
| Клиент в приложении | фальшивая служба на `QLocalServer` в самом тесте |
| Служба целиком | подставные драйверы, настоящий канал |
| Драйверы COM | виртуальная пара портов (`com0com`) |
| Драйвер принтера | печать в файл, проверка ZPL |
| Сквозной сценарий | служба подпроцессом + приложение offscreen |

Отдельно — отладочная консоль службы, которая вбрасывает события руками:
`cli scan WH…`, `cli weight 22.4 --stable`, `cli device printer offline`. Ею
проверяются сценарии, иначе воспроизводимые только выдёргиванием проводов.

Сейчас из этого написана только отладочная консоль и окно симулятора
(`devices/simulator.py`) — оба вбрасывают события через канал вручную. Тестов
нет ни на одном уровне.

Режим подмены устройств задуман **поролевым**, а не общим: симулятор
подключается к службе и забирает себе отдельные роли, поэтому возможна
комбинация «весы настоящие, сканер поддельный, принтера нет». Как это устроено —
[devices-simulation.md](devices-simulation.md).

## 7.1 Шрифты интерфейса

Дизайн свёрстан стеком `Barlow / Barlow Condensed, system-ui, sans-serif`, но
**в Barlow нет кириллицы** (латиница, latin-ext, вьетнамский). В исходном
рендере весь русский текст и так рисовался запасным `system-ui`, а Barlow
доставался только латинице и цифрам.

Поэтому приложение берёт **Segoe UI**, заголовки — `font-weight: 600` (Windows
подставляет Segoe UI Semibold). Это ровно то, что показывал браузер.

Класть Barlow в `desktop/app/assets/fonts/` не стоит: латиница пойдёт
одним шрифтом, кириллица другим. Если понадобится узкий «чертёжный» вид, нужен
шрифт с кириллицей — Roboto Condensed, PT Sans Narrow, Fira Sans Condensed:
достаточно положить `.ttf` в ту же папку и указать семейство в
`desktop/app/fonts.py`.

## 8. Порядок работ

**Оборудование** (можно начинать сразу, от сервера не зависит):

1. `protocol.py` — команды и события, общий модуль.
2. Клиент в приложении поверх `QLocalSocket`, проверяется заглушкой.
3. Служба с драйверами, запускается в терминале.
4. Сборка `devices.exe`, запуск дочерним процессом.

**Сервер:**

1. ~~Контракт и схема: OpenAPI, модели, первая миграция, сид.~~ Готово:
   [api.md](api.md), [openapi.json](openapi.json), `backend/database`.
2. ~~Десктоп на API.~~ Готово: все одиннадцать экранов, пагинация и фильтры на
   сервере, клиент в [desktop/app/api](../desktop/app/api).
3. Ядро сервера: auth, справочники, остатки, заказы, с тестами.
4. Отгрузка, приёмка, движения склада.
5. Обвязка: логи, метрики, бэкапы, CI, деплой.

Порядок 2 и 3 поменялся местами против первоначального плана — сознательно.
Приложение перевели на готовое описание API раньше, чем написали сервер, и это
вскрыло семь несоответствий в контракте до того, как под них был написан код:
четыре при переводе ядра склада (`by_warehouse`, `responsible`, `users`,
`unit_weight`) и три позже (`in_stock`, `/users/{id}/activity`, ключ товара).
Дешевле поправить документ, чем реализацию.

Что не понадобилось: отдельный слой репозиториев и переключатель источника.
Экраны зовут `api.client` напрямую — прослойка ради одной реализации была бы
пустой. Осталось фоновое выполнение запросов: сейчас всё синхронно, и на
медленной сети окно подмерзает.

## 9. Открытые вопросы

1. **Модели сканера, весов и принтера** — от них зависят протокол разбора
   показаний, язык команд принтера и режим работы сканера.
2. **Нужна ли работа офлайн** с последующей синхронизацией — это отдельная
   очередь операций и заметно больше кода.
3. **Нужен ли обмен с 1С** — тогда `code1c` становится ключом интеграции и нужны
   эндпоинты выгрузки.
4. **Один склад или несколько** с разными пользователями — от этого зависит,
   попадает ли `warehouse_id` в каждый запрос.
