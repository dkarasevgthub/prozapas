# ProЗапас

Складской учёт для компании с несколькими складами: десктоп на PyQt6, API на FastAPI
и отдельная служба, которая держит сканер, весы и принтер этикеток.

Идея: заказ — это перемещение товара между двумя складами. Одна запись, которую две
стороны видят по-разному: кому привезут — принимает, у кого заказали — отгружает.
Направление не хранится, а вычисляется от того, кто смотрит.

```
  Десктоп (PyQt6) ──HTTPS/JSON──► FastAPI ──► PostgreSQL
        │                       RBAC, транзакции, OpenAPI
        │
        └──именованный канал──► Служба устройств ──► сканер · весы · принтер
                                {"cmd":"print"} / {"event":"scan"}

  создал заказ ──► processing ──► резерв ──► shipped ──► списание у отправителя
                                                            │
                     оприходование у получателя ◄── received ◄── сканирование коробок
```

## Эндпоинты

```
POST   /auth/login                       вход, отдаёт JWT
GET    /bootstrap                        склады, роли, права, текущий пользователь
GET    /dashboard                        счётчики и лента событий

GET    /orders                           заказы своего склада
POST   /orders/{id}/accept|decline|cancel   смена статуса        (orders: edit)

GET    /shipments/{order_id}             отгрузка по заказу
POST   /shipments/{order_id}/boxes       коробка со штрихкодом   (shipping: edit)
POST   /shipments/{order_id}/ship        отгрузить, списать      (shipping: edit)

GET    /receipts/{order_id}              приёмка по заказу
POST   /receipts/{order_id}/boxes/{barcode}/receive   скан коробки
POST   /receipts/{order_id}/complete     принять, оприходовать   (receiving: edit)

GET    /stock, /catalog, /users, /permissions   справочники и остатки

POST   /catalog/import, /stock/import    загрузить XML из 1С (CommerceML 2)
GET    /catalog/export, /stock/export    выгрузить XML для 1С
```

Всего 50 операций, контракт — [docs/api.md](docs/api.md). Реализованы все разделы;
`backend/tests` держит их под тестами на настоящем Postgres, включая сверку
живой схемы с [docs/openapi.json](docs/openapi.json).

## Каталоги

```
desktop/app       клиент: справочник, остатки, заказы, отгрузка, приёмка, пользователи
desktop/devices   служба устройств: драйверы, канал, очередь печати, симулятор
backend/api       роутеры → сервисы → модели, слои проверяются разбором импортов
backend/database  SQLAlchemy 2.0, 16 таблиц, миграции Alembic
docs              контракт API, архитектура, ТЗ на службу устройств
```

## Запуск

Три части поднимаются независимо, каждая одной командой из чистого клона.
Ничего подготавливать заранее не нужно: `uv run` сам создаст `.venv` по локу,
а `make up` — свой `.env`.

**API** — Postgres, миграции, данные стенда и сервер, всё в Docker:

```
cd backend && make up
```

Слушает `127.0.0.1:8000`, Swagger — на `/api/v1/docs`. `.env` соберётся из
`.env.example`, если его ещё нет. Вход: логин `admin`, пароль — `SEED_PASSWORD`
из `.env`, он же у всех остальных учёток сида. Остановить, сохранив данные —
`make down`; снести базу и собрать заново — `make reset`.

**Приложение** — клиент; служба устройств поднимается вместе с ним и гаснет
вместе с ним, отдельно её запускать не нужно:

```
cd desktop && uv run main.py
```

Адрес сервера по умолчанию — `http://127.0.0.1:8000/api/v1`, то есть локальный
`make up` подхватывается без настройки. Другой адрес — `PROZAPAS_API` в
`desktop/.env` (см. `desktop/.env.example`).

**Симулятор оборудования** — окно с кнопками вместо сканера, весов и принтера.
Открывается вместе с приложением в независимом окне, автоматически подключается
к службе и включает эмуляцию всех трёх устройств. Его можно использовать при
открытых диалогах приложения и сворачивать отдельно. При закрытии основного окна закрываются симулятор
и запущенная приложением служба. Для работы с настоящим оборудованием задайте
`PROZAPAS_SIMULATOR=false` в `desktop/.env`.
В режиме симулятора служба не ищет реальное оборудование: снятие `attach`
делает соответствующее устройство недоступным, повторное включение возвращает его онлайн.

Администратор может выбрать установленный принтер Windows в блоке
«Оборудование» → «Настроить принтер». Выбор сохраняется на рабочем месте
для текущего пользователя Windows и используется всеми учётными записями
приложения после его перезапуска. Он имеет приоритет над именем принтера в `.env`.
Кнопка «Логи» также доступна только администратору; при выходе из его
учётной записи открытый журнал устройств закрывается.

Симулятор можно запустить отдельно и выбрать устройства вручную:

```
cd desktop && uv run python -m devices.simulator
```

Подробности — [docs/devices-simulation.md](docs/devices-simulation.md). Там же
про `python -m devices.cli` — то же самое из консоли, без окна.

## Сборка Windows

```powershell
cd desktop
uv run --group build build.py
```

Результат — `desktop/dist/ProZapas.exe`, один файл с приложением, службой устройств,
симулятором и ресурсами. На компьютере пользователя Python не требуется.
Настройки из `desktop/.env` включаются в сборку, поэтому адрес API должен быть
задан до запуска сборки. Файл `.env` рядом с готовым `.exe` переопределяет
встроенные настройки. Текущая сборка подключается к `https://185.196.117.2/api/v1`
с проверкой HTTPS-сертификата.

## Окружение

Зависимости ставит [uv](https://docs.astral.sh/uv/) по `pyproject.toml` и `uv.lock`,
свои у `desktop/` и у `backend/`. Виртуальное окружение создаётся в `.venv` рядом
с `pyproject.toml`, активировать его не нужно — команды идут через `uv run`.

```
cd desktop && uv sync             # поставить зависимости, не запуская клиент
uv run python -m devices          # служба устройств отдельно от приложения

cd backend && uv sync             # для IDE; сами сервисы живут в Docker
make test                         # тесты API на отдельной базе prozapas_test
                                  # остальные цели — в backend/Makefile
```

Новая зависимость — `uv add <пакет>` в нужном каталоге; `uv.lock` коммитится.

## Ветки и выпуск изменений

- `dev` — текущая разработка и локальные проверки.
- `main` — принятые изменения; объединение выполняется через Pull Request.
- `deploy` — версия для сервера, автоматически обновляется из `main` после успешных тестов.

Код, тесты и конфигурации локального и серверного запуска хранятся во всех ветках.
Настоящие `.env`, пароли, базы и сборки `.exe` в Git не попадают.

Обычный порядок работы:

```sh
git switch dev
git pull --ff-only
# Изменить код, проверить локально и сделать коммит.
git push origin dev
```

Затем откройте Pull Request `dev` → `main` и объедините его после успешных
`Backend tests`, `Desktop tests` и `System tests`. Пуши в `dev` и проверки Pull Request сервер
не обновляют. После принятия изменений в `main` Actions повторяет проверки,
переносит этот же коммит в `deploy` без переписывания истории и запускает деплой.
В `deploy` отдельные правки не вносят.

После выпуска обновите рабочую ветку, сохраняя историю слияний:

```sh
git switch dev
git pull --ff-only
git merge origin/main
git push origin dev
```

Локальный запуск использует `backend/docker-compose.yaml`; сервер —
`deployment/compose.yaml`. Подробности развёртывания: [deployment/README.md](deployment/README.md).

## Автоматические проверки

CI проверяет три группы сценариев; все три обязательны перед выпуском:

- **Backend tests:** весь набор API на PostgreSQL, миграции, роли, точность остатков,
  обмен с 1С и контракт. Отчёты JUnit и покрытие строк/ветвлений доступны в артефакте
  `backend-test-results`; снижение общего покрытия ниже 90% блокирует CI.
  Отдельно проверяются защита SSH и веток, резервная копия
  перед миграциями и восстановление предыдущего API при неудачной выкладке.
- **Desktop tests (Windows):** права интерфейса, HTTP-клиент, штатный запуск и
  остановка службы, очередь печати и обработка ошибок Windows spooler. Внешний
  JSON/IPC-клиент запускает службу отдельным процессом и проверяет её протокол,
  события, отключение устройств, переподключение и байты этикеток. Затем CI собирает
  `.exe` и повторно проверяет упакованную службу тем же внешним клиентом.
  Полные сценарии Qt-интерфейса и конкурирующие HTTP-запросы также проходят
  на Windows с отдельным PostgreSQL; отчёты — `windows-system-test-results`.
- **System tests (Linux):** Qt-формы работают с настоящим HTTP API и отдельной
  базой `prozapas_system_test`. Проверяются полный перенос товара через разные роли,
  частичная отгрузка/недостача, ручной вес, дробная упаковка, каталог, складские операции,
  пользователи, вход/выход и восстановление сессии. Параллельные HTTP-запросы проверяют
  идемпотентность и защиту от двойного резерва/упаковки. Виртуальные последовательные
  порты подают реальные байтовые потоки драйверам сканера и весов. Реальный `pg_dump`
  восстанавливается в `prozapas_restore_test`, после чего сравниваются все таблицы,
  счётчики идентификаторов, столбцы, ограничения и индексы.
  Скриншоты, журнал API и результат восстановления доступны в `system-test-results`.

Служба не оценивает сама себя: внешний проверяющий клиент не импортирует `devices`
и не вызывает `--self-check`. Файловый приёмник печати проверяет содержимое и число
копий, а подмена системного spooler проверяет Windows-вызовы и повторные попытки.
Физическую печать, качество этикетки и конкретную модель оборудования проверяют
на рабочем месте; CI использует виртуальные порты и транспорт печати в файл.

Локальные тесты приложения и устройств:

```powershell
cd desktop
$env:QT_QPA_PLATFORM = 'offscreen'
uv run --locked python -m unittest discover -s tests -v
```

Сквозной набор требует локального PostgreSQL и установленных зависимостей обоих
проектов. Переменная `SYSTEM_DATABASE_URL` должна указывать на отдельную локальную
базу **строго** `prozapas_system_test`; её содержимое пересоздаётся тестовым запуском:

```sh
SYSTEM_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@127.0.0.1:5432/prozapas_system_test \
  backend/.venv/bin/python deployment/run_system_tests.py
```
